# WSA-Enterprise — Full Docker Container Recovery, Inspection & Verification
## 1. Authorization and Objective
نفّذ استعادة تشغيلية مضبوطة لمشروع WSA-Enterprise المحلي الموجود في:
`G:\WSA-Enterprise`
أُعيد تشغيل PostgreSQL الأصلية بنجاح، وأصبحت تعمل على المنفذ TCP 5432 باستخدام قاعدة البيانات الأصلية وVolume الأصليين.
النتائج المؤكدة من آخر تقرير تنفيذ:
- Windows service `postgresql-x64-17` متوقفة، وStartType ما زال Automatic.
- الحاوية `wsa-enterprise-postgres-1` تعمل.
- قاعدة البيانات `wsa_enterprise` تقبل الاتصالات.
- PostgreSQL version: 16.14.
- Volume: `wsa-enterprise_postgres_data`.
- جدول `migrations` موجود ويحتوي على 55 صفًا.
- جدول `cghia_capability_cell_records` غير موجود.
- Redis وBackend لا يزالان متوقفين.
- الحاوية اليتيمة `wsa-enterprise-postgres-1-orphan` لا تزال متوقفة.
**الهدف:** استعادة الخدمات الأصلية المطلوبة، وفحص جميع حاويات المشروع الموجودة، والتحقق من صحتها واتصالاتها وتحديد سبب أي فشل.
## 2. Core Safety Rules
نفّذ العمل فعليًا باستخدام الأوامر المتاحة في بيئة Windows وDocker Desktop، ولا تكتفِ بتقديم خطة.
- استخدم الحاويات الموجودة عندما تكون مطابقة للإعدادات التاريخية.
- افحص الحالة قبل كل إجراء، وتحقق من النتيجة بعده.
- لا تنشئ حاويات بديلة ولا تعِد إنشاء حاويات موجودة.
- لا تحذف أو تعيد تهيئة أو تستبدل أي Volume.
- لا تنفّذ migrations أو restore أو seeders.
- لا تعدّل `.env` أو ملفات Compose أو ملفات التطبيق أو إعدادات قاعدة البيانات.
- لا تنفّذ Git commit أو push أو reset أو clean.
- لا تستخدم `docker compose down` أو `docker compose down -v`.
- لا تستخدم `docker system prune` أو `docker volume prune`.
- لا تشغّل الحاوية `wsa-enterprise-postgres-1-orphan`.
- لا تشغّل حاويات الاختبار أو أي حاوية غير تابعة لمسار التشغيل المطلوب دون سبب موثق وموافقة منفصلة.
- لا توقف خدمات Windows إضافية.
- لا تطبع كلمات المرور أو الأسرار أو قيم Environment الحساسة.
- لا تدّعِ نجاح أي فحص لم يُنفذ فعليًا.
إذا اكتشفت تعارضًا أو خطرًا على البيانات أو حاجة إلى تغيير غير مصرح به، توقف عن الإجراء المتأثر، وسجّل السبب والنتائج، ثم تابع فقط الفحوص المستقلة الآمنة.
## 3. Phase A — Inventory of All Docker Containers
اجمع قائمة شاملة بالحاويات الموجودة حاليًا، بما فيها الحاويات المتوقفة.
لكل حاوية مرتبطة بالمشروع، افحص:
- الاسم والحالة وExit Code.
- صورة Docker وإصدارها.
- تاريخ آخر تشغيل وإيقاف، إن كان متاحًا.
- منافذ Host-to-Container.
- الشبكات.
- Volumes وMounts.
- Restart Policy.
- Compose project/service/profile labels.
- سجلات التشغيل الأخيرة.
- اعتمادها على الخدمات الأخرى.
- ما إذا كانت جزءًا من التشغيل التاريخي أو خدمة اختبار أو حاوية مؤقتة.
صنّف النتائج إلى:
1. خدمات التشغيل الأساسية.
2. خدمات واجهة المستخدم والويب.
3. Queue وScheduler.
4. خدمات البحث العلمي والتخزين الإضافي.
5. حاويات الاختبار والتحقق المؤقت.
6. الحاويات اليتيمة أو غير المرتبطة بوضوح بمسار التشغيل.
لا تعتبر كل حاوية متوقفة حاوية يجب تشغيلها.
## 4. Phase B — Validate the Existing PostgreSQL
لا تُعد تشغيل PostgreSQL ما دامت تعمل بشكل سليم.
تحقق من:
- أن `wsa-enterprise-postgres-1` تعمل.
- أن Volume الأصلي `wsa-enterprise_postgres_data` ما زال مرتبطًا بها.
- أن المنفذ `5432:5432` مرتبط بها.
- نجاح `pg_isready`.
- نجاح الاتصال بقاعدة `wsa_enterprise` باستخدام المستخدم `wsa`.
- وجود جدول `migrations`.
- وجود جدول `cghia_capability_cell_records` أو غيابه.
- عدم وجود أخطاء جديدة حرجة في سجلات الإقلاع.
استخدم استعلامات قراءة فقط. لا تحاول إنشاء الجدول المفقود أو تشغيل migrations لمعالجة غيابه.
## 5. Phase C — Restore Redis
قبل التشغيل:
- افحص الحاوية الأصلية `wsa-enterprise-redis-1`.
- تحقق من الصورة والـ Volume والمنفذ والشبكة وRestart Policy.
- تحقق من عدم وجود تعارض مع خدمة أخرى تستخدم TCP 6379.
إذا كانت الحاوية الأصلية موجودة ومطابقة للتكوين المتوقع والمنفذ متاحًا، شغّلها باستخدام `docker start` فقط.
بعد التشغيل:
- تحقق من بقائها Running.
- نفّذ فحص صحة غير تعديلي، مثل `redis-cli ping` باستخدام إعدادات الحاوية الحالية.
- راجع السجلات بحثًا عن أخطاء بدء التشغيل.
- لا تنفّذ FLUSH أو RESET أو أي عملية تغيّر بيانات Redis.
إذا فشلت، لا تعِد إنشاء الحاوية ولا تغيّر إعداداتها تلقائيًا.
## 6. Phase D — Restore Backend
لا تشغّل Backend إلا بعد نجاح فحوص PostgreSQL وRedis.
افحص الحاوية الأصلية `wsa-enterprise-backend-1`:
- الصورة وإصدارها.
- الشبكة.
- إعداد الاتصال بقاعدة البيانات دون طباعة الأسرار.
- إعداد Redis.
- Mounts وVolumes.
- السجلات السابقة.
- Health Check، إن كان معرفًا.
إذا كانت الحاوية الأصلية موجودة وإعداداتها مطابقة، شغّلها باستخدام `docker start` فقط.
تحقق من:
- بقائها Running.
- نجاح اتصالها بقاعدة البيانات الأصلية.
- نجاح اتصال Redis، إذا كان التطبيق يعتمد عليه.
- عدم وجود أخطاء Fatal أو أخطاء اتصال متكررة في السجلات.
- نجاح فحص صحة التطبيق المتاح، إن وجد.
لا تشغّل migrations أو أوامر Artisan التي تكتب في قاعدة البيانات.
إذا كان غياب `cghia_capability_cell_records` يسبب فشلًا، سجّل الخطأ وتوقف عن أي إصلاح. لا تُنشئ الجدول ولا تغيّر المخطط.
## 7. Phase E — Inspect and Classify Every Remaining Container
افحص جميع حاويات المشروع الأخرى، بما فيها:
- nginx.
- frontend.
- queue.
- scheduler.
- حاويات R7 أو Scientific Store إن كانت موجودة.
- حاويات الاختبار.
- حاويات التحقق من النسخ الاحتياطية.
- الحاويات اليتيمة.
لكل حاوية، حدّد:
- هل هي مطلوبة لتشغيل المشروع حاليًا؟
- هل كانت تعمل في الحالة التاريخية الموثقة؟
- هل يمكن تشغيلها دون إعادة إنشائها أو تعديل إعداداتها؟
- هل تعتمد على خدمة لم تُستعد بعد؟
- هل تحتوي على بيانات أو Volumes يجب حمايتها؟
- هل يوجد تعارض في المنافذ أو الشبكات؟
**قواعد التشغيل:**
أ. شغّل فقط الخدمات الأصلية اللازمة لمسار التطبيق الأساسي، عندما تكون مطابقة للتكوين المتوقع وتنجح بوابات السلامة.
ب. لا تشغّل `nginx` أو `frontend` أو `queue` أو `scheduler` تلقائيًا لمجرد وجودها. افحصها أولًا وحدد ما إذا كانت مطلوبة لتحقيق هدف التشغيل الحالي.
ج. لا تشغّل حاويات الاختبار أو النسخ الاحتياطي المؤقت أو الحاويات اليتيمة تلقائيًا.
د. لا تشغّل حاويات متعددة تستخدم PostgreSQL data directory نفسه في الوقت نفسه.
هـ. لا تشغّل حاوية إضافية لخدمة تخزين علمي أو R7 إلا بعد إثبات وظيفتها واعتمادها على البيانات والتكوين الصحيحين، ودون تغيير مخطط أو بيانات.
و. إذا كان تشغيل أي حاوية يتطلب إعادة إنشائها أو تغيير منفذها أو تعديل Volume أو تغيير إعداداتها، اتركها متوقفة وسجّل سبب ذلك.
## 8. Phase F — Network and Application Connectivity
افحص:
- شبكة Compose الأصلية `wsa-enterprise_wsa`.
- اتصال Backend بخدمة PostgreSQL عبر اسم الخدمة الداخلي `postgres`.
- اتصال Backend بـRedis عبر اسم الخدمة الصحيح في الإعدادات الحالية.
- منافذ Host المنشورة.
- أي تعارضات بين الحاويات وخدمات Windows.
- حالة الخدمات التي تعتمد على بعضها.
لا تغيّر الشبكات أو المنافذ أو أسماء الخدمات أو إعدادات DNS تلقائيًا.
اختبر الاتصال بأدوات قراءة أو Health Checks غير تعديلية، ولا تنفّذ اختبارات وظيفية قد تكتب في قاعدة البيانات.
## 9. Phase G — Final Verification of All Containers
بعد استكمال إجراءات الاستعادة المصرح بها، أعد جرد الحاويات مرة أخرى.
قدّم جدولًا نهائيًا يحتوي على:
| Container | Previous Status | Final Status | Health | Ports | Data Volume | Verification |
|---|---|---|---|---|---|---|
لكل حاوية، وضّح ما إذا كانت:
- استُعيدت بنجاح.
- تعمل ولكن Health Check غير متاح.
- فشل تشغيلها.
- تُركت متوقفة عمدًا.
- حاوية اختبار أو يتيمة لا ينبغي تشغيلها.
ثم قدّم ملخصًا يوضح:
- عدد الحاويات الموجودة.
- عدد الحاويات العاملة.
- عدد الحاويات المتوقفة.
- عدد الحاويات التي فشلت.
- الخدمات الأساسية التي نجحت فحوصها.
- نتائج اتصال Backend بـPostgreSQL وRedis.
- أي تعارضات في المنافذ.
- أي أخطاء جديدة في السجلات.
- أي اختلافات عن الحالة التاريخية.
- ما إذا كان المشروع قابلًا للاستخدام فعليًا أم أن التشغيل جزئي فقط.
