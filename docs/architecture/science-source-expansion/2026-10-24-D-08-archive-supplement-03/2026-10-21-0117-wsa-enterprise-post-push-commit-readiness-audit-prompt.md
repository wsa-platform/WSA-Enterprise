# WSA-Enterprise — Post-Push Commit Readiness Audit

## 1. الدور والهدف

تصرف كمهندس برمجيات خبير في Laravel وPHP وGit، ومراجع معماري مسؤول عن سلامة التبعيات والاختبارات والتاريخ البرمجي.

المهمة هي استكمال التدقيق بعد نجاح دفع مجموعة `MissionArtifactArchive`، وتحديد جميع المجموعات الأخرى التي يمكن اعتمادها للـ Commit، مع أدلة فعلية لكل مجموعة.

المطلوب ليس مجرد سرد الملفات؛ المطلوب فحص التغييرات الفعلية، وترابطها، واختباراتها، وتحديد حدود كل Commit آمن ومستقل.

**في هذه الجولة: تدقيق وتحليل فقط. لا تنشئ Commit ولا تنفذ Push ولا تعدّل ملفات المشروع.**

## 3. قواعد السلامة غير القابلة للتفاوض

1. ابدأ بفحص الحالة الحالية في جميع Worktrees ذات الصلة، دون تغييرها.
2. لا تفترض أن أي تقرير سابق ما زال حديثًا؛ تحقق من Git والملفات الفعلية.
3. لا تستخدم:
   - `git add`
   - `git commit`
   - `git push`
   - `git pull`
   - `git merge`
   - `git rebase`
   - `git cherry-pick`
   - `git reset`
   - `git clean`
   - `git stash`
   - أو أي أمر يغيّر محتوى ملفات العمل أو تاريخ Git.
4. لا تحذف أو تعِد تسمية أو تستعد أي ملف.
5. لا تحذف أو تعدّل Worktrees أو الفروع المؤقتة.
6. لا تعدّل ADR-021 أو ADR-023.
7. لا تنفّذ أي Migration أو تغييرات على قواعد البيانات.
8. لا تكشف كلمات المرور أو الرموز أو محتوى الأسرار في التقرير.
9. لا تشغّل اختبارًا يحتمل أن يكتب إلى SQLite التشغيلية أو PostgreSQL التشغيلية.
10. لا تعِد تنفيذ فحوص سبق نجاحها ما لم يوجد سبب جديد موثق.
11. إذا احتاج فحص معين إلى تعديل أو اختبار خطر، صنّفه «يحتاج تحققًا إضافيًا» بدلًا من تنفيذه.

يمكن استخدام أوامر القراءة والاختبارات التي ثبت أنها معزولة وآمنة فقط.

## 4. المرحلة الأولى — جرد Git الحالي

افحص المستودع الأصلي وWorktrees المرتبطة به.

في المستودع الأصلي، سجّل:

- `git status -sb`
- `git status --short`
- `git branch --show-current`
- `git rev-parse HEAD`
- `git fetch origin`
- `git rev-parse origin/phase-18-m18-ai-marketing-communications`
- `git log --graph --oneline --decorate -15`
- `git diff --stat`
- `git diff --cached --stat`
- `git diff --check`
- `git worktree list`

استخدم `fetch` لتحديث معلومات التتبع فقط، دون دمج أو سحب التغييرات.

تحقق من الملفات غير المتعقبة وعددها الفعلي، ولا تعتمد على الأعداد السابقة.

افحص Worktrees الموجودة للتأكد من الفرع وHEAD وحالة الشجرة، دون تبديل الفروع أو تعديلها.

أنشئ خريطة واضحة لما يلي:

- الالتزامات المحلية والبعيدة.
- التعديلات المتعقبة غير الملتزم بها.
- الملفات غير المتعقبة.
- أي ملفات مشتركة بين أكثر من مجموعة.
- أي اختلاف تاريخي قد يمنع إنشاء Commit مستقل وآمن.

لا تحاول إصلاح اختلافات Git في هذه المرحلة.

## 6. المرحلة الثالثة — فحص التبعيات قبل اقتراح أي Commit

لكل مجموعة مرشحة:

1. اقرأ كامل الفرق الفعلي، لا ملخص `git diff --stat` فقط.
2. حدد الأصناف والعقود التي تستوردها الملفات.
3. تحقق من وجود كل صنف أو عقد مطلوب، ومن عدم اعتماد التنفيذ على ملف غير متعقب مستبعد.
4. حدد ما إذا كانت هناك تغييرات لازمة في Service Providers أو إعدادات أو Composer.
5. افحص الاختبارات الموجودة ومدى تغطيتها للسلوك الأساسي وحالات الفشل.
6. تحقق من عدم وجود API أو واجهة داخلية مكسورة بسبب فصل المجموعة.
7. حدد إن كان هناك توثيق مطلوب لتفسير التغيير.
8. افحص `git diff --check` على الملفات المعنية.
9. ميّز بين عيب مؤكد ومجرد احتمال يحتاج دليلًا إضافيًا.

لا تصف المجموعة بأنها «جاهزة» إذا كانت تعتمد على ملف غير متعقب لم يُراجع، أو اختبار غير معزول، أو إعداد لم يُتحقق منه.

## 7. المرحلة الرابعة — الاختبارات المسموح بها

استخدم نتائج الاختبارات السابقة إذا كانت مرتبطة بنفس SHA ونفس محتوى الملفات.

يمكن إعادة تشغيل اختبارات وحدة محددة فقط عندما تتوفر أدلة على أنها لا تكتب خارج مجلد الاختبار.

اختبار MissionArtifactArchive سبق أن نجح بنتيجة 9 اختبارات و40 تأكيدًا، وجرى دفع المجموعة بنجاح؛ لا تعِد تشغيله لمجرد تكرار النتيجة.

لا تشغّل:

- مجموعة LocalIndex التي قد تلمس SQLite التشغيلية.
- اختبارات PostgreSQL غير المعزولة.
- اختبارات قد تحذف أو تعدل بيانات من قاعدة تشغيلية.
- أي Migration.
- أي أمر حصاد أو أرشفة على بيانات التشغيل.

إذا كانت الاختبارات تحتاج بيئة معزولة غير متاحة، وثّق المتطلبات وصنّف المجموعة بأنها تحتاج تحققًا إضافيًا.

## 8. المرحلة الخامسة — تقييم الجاهزية

صنّف كل مجموعة في إحدى الحالات التالية:

### READY_FOR_COMMIT
- الفرق مفهوم ومراجع.
- التبعيات كاملة.
- لا توجد أسرار أو بيانات تشغيلية.
- الاختبارات المطلوبة نجحت أو يوجد مبرر موثق لقبول النطاق دون اختبارات إضافية.
- لا يوجد تعارض Git أو توثيقي غير محسوم يمنع الالتزام.

### READY_AFTER_STAGING_REVIEW
- المجموعة مرشحة بقوة.
- تحتاج مراجعة نهائية لقائمة الملفات ومنطقة التجهيز.
- لا توجد حاجة إلى تعديل جوهري.

### NEEDS_TESTS
- التبعيات واضحة، لكن الاختبارات المطلوبة لم تُنفّذ أو لم تُعزل.

### NEEDS_FIX
- يوجد خلل مؤكد أو تعارض أو نقص في التبعيات أو الإعدادات.

### BLOCKED
- تعتمد على قرار معماري غير محسوم، أو على ملفات لا يمكن ضمها بأمان، أو على بيانات تشغيلية غير قابلة للعزل.

### EXCLUDED
- بيانات مؤقتة أو حساسة أو مخرجات تشغيل غير مناسبة للـ Commit.

لا تستخدم READY لمجرد أن الملفات موجودة أو أن بعض الاختبارات نجحت.

## 9. المرحلة السادسة — اقتراح خطة Commit

بعد مراجعة جميع المجموعات، أنشئ جدولًا يتضمن:

| الحقل | المطلوب |
|---|---|
| المجموعة | الاسم الوظيفي |
| المسارات | قائمة دقيقة أو نمط محدد مع بيان الملفات الفعلية |
| الغرض | الوظيفة التي تحققها |
| التبعيات | المجموعات التي يجب أن تسبقها |
| الاختبارات | الاختبارات الموجودة ونتائجها الفعلية |
| المخاطر | أي خطر متبقٍ |
| الحالة | إحدى حالات الجاهزية المحددة |
| القرار | Commit مستقل، دمج مع مجموعة أخرى، إصلاح، أو استبعاد |
| عنوان Commit | عنوان مقترح عند استحقاقه |

رتّب المجموعات الجاهزة حسب التبعيات، مع اقتراح عنوان واضح لكل Commit.

افصل التوثيق عن الكود متى كان ذلك آمنًا معماريًا، ولا تفصل ملفات لا يعمل أحدها دون الآخر.

إذا لم توجد أي مجموعة إضافية جاهزة، قل ذلك بوضوح ولا تخترع مرشحين.

## 10. المرحلة السابعة — شروط إنهاء المهمة

لا تنفذ أي تغييرات أو عمليات Git معدِّلة.

لا تستخدم `git add` ولا تنشئ منطقة تجهيز جديدة.

لا تنفذ Commit أو Push.

لا تُصلح المشكلات المكتشفة في هذه الجولة؛ وثّقها ضمن تقرير الإصلاحات المطلوبة.

إذا ظهرت حاجة إلى خطوة خطرة أو غير مصرح بها، توقف عند التحليل واشرح السبب.

## 11. التقرير النهائي بالعربية

أرسل تقريرًا واحدًا شاملًا يحتوي:

1. الحالة الفعلية لـ Git والفروع وWorktrees.
2. العدد الفعلي للمسارات المتعقبة المعدّلة وغير المتعقبة.
3. المجموعات التي تمت مراجعتها.
4. قائمة دقيقة بالمجموعات الجاهزة فعلًا للـ Commit.
5. قائمة المجموعات التي تحتاج اختبارات أو إصلاحات، مع السبب المحدد.
6. قائمة الملفات المستبعدة لأسباب تتعلق بالأسرار أو البيانات المؤقتة.
7. نتائج الاختبارات التي شُغّلت فعليًا، مع الأعداد ورموز الخروج.
8. المخاطر والتبعيات غير المحسومة.
9. ترتيب Commit المقترح وعنوان كل التزام.
10. أول مجموعة توصي بتنفيذها في الجولة التالية.
11. تأكيد أن المهمة لم تعدّل أي ملف، ولم تنشئ Commit أو Push، ولم تغيّر أي Worktree أو قاعدة بيانات.

لا تكتفِ بإعادة التقرير السابق؛ المطلوب استكماله والتحقق من الحالة الحالية فعليًا، مع تجنب إعادة الاختبارات أو التدقيقات التي لا تضيف دليلًا جديدًا.

**معيار النجاح:** قائمة دقيقة قابلة للتنفيذ للمجموعات الجاهزة، مع أدلة واضحة وحدود Commit آمنة، دون تعريض أي عمل قائم للفقد أو التداخل.
