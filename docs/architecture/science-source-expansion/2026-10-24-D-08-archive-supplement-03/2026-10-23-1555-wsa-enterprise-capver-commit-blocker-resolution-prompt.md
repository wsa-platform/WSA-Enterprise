## 3. المرحلة الأولى — التحقق من حالة Git

ابدأ مباشرةً بالفحص للقراءة فقط، دون إرسال خطة تمهيدية.

من داخل `G:\WSA-Enterprise`، تحقق من:

1. الفرع الحالي.
2. قيمة HEAD.
3. حالة Git باستخدام `git status --porcelain=v1`.
4. حالة الفهرس، وهل يحتوي أي تغييرات staged.
5. اسم upstream إن كان متاحًا.
6. آخر خمسة commits.
7. عدد الملفات المتعقبة المعدّلة وغير المتعقبة والمحذوفة.
8. حالة الملفات التشغيلية المحمية، دون فتحها للكتابة.

يمكن استخدام أوامر Git للقراءة فقط، مثل:

```powershell
git rev-parse --abbrev-ref HEAD
git rev-parse HEAD
git status --porcelain=v1
git diff --cached --stat
git rev-parse --abbrev-ref --symbolic-full-name '@{u}'
git log --oneline -5
```

إذا كان الفرع أو HEAD مختلفًا عن المتوقع:

- توقف عن بقية الفحوص التي تعتمد على خط الأساس المتوقع.
- لا تحاول إعادة الفرع أو إصلاح الحالة.
- وثّق القيم الفعلية وسبب توقف المراجعة.
- لا تغيّر أي شيء.

إذا كانت الحالة مطابقة، تابع.

- حالة Git.

### 4.2 الملفات غير المتعقبة

الملفات غير المتعقبة لا تظهر بالضرورة في `git diff` العادي. لذلك افحص قائمة هذه الملفات ومحتواها بطريقة قراءة فقط.

صنّفها إلى:

- ملفات مصدر.
- ملفات اختبارات.
- ملفات إعداد.
- وثائق وقرارات معمارية.
- تقارير.
- ملفات تشغيل أو قواعد بيانات.
- مخرجات مؤقتة.
- ملفات أخرى غير محسومة.

لا تضف أي ملف إلى Git. ولا تعتبر الملف غير المتعقب مخرجًا مؤقتًا دون فحص محتواه وموقعه.

إذا تعذر قراءة ملف أو تعذر تحديد وظيفته، سجّل ذلك صراحةً.

### 4.3 فحص أمني

افحص التغييرات والملفات ذات الصلة بحثًا عن:

- أسرار أو مفاتيح فعلية.
- كلمات مرور أو رموز وصول.
- ملفات `.env`.
- ملفات قواعد بيانات أو نسخ احتياطية.

- أي بيانات شخصية أو تشغيلية غير مناسبة للنشر.

## 8. المرحلة السادسة — حسم ADR-023

الملف:

`docs/architecture/ADR-023-scientific-source-expansion.md`

راجع §§8.60–8.71 بالرجوع إلى `HEAD` والنسخة المحلية.

### 8.1 المقارنة

استخدم قراءة Git ومقارنة نصية لا تغيّر الملف. حدّد:

- الأقسام الموجودة في `HEAD`.
- الأقسام الموجودة محليًا.
- الأقسام الجديدة محليًا.
- أي تعديل أو حذف أو إعادة صياغة في النص التاريخي.
- الفروق في ترتيب الأقسام ونهايات الأسطر عند ارتباطها بالتحقق.

لا تنشئ ملفات مقارنة داخل المستودع ولا تستخدم إعادة كتابة النص كطريقة غير متحققة لحساب البصمة.

### 8.2 خيارات القرار

**الحالة A — §§8.66–8.70 محلية غير منشورة**

لا تفترض أن ذلك يجيز نشرها تلقائيًا مع §8.71.

تحقق من محتواها وتفويضها المعماري وحالة مراجعتها. وضّح ما إذا كان يمكن نشرها معًا بأمان، وما إذا كانت تحتاج إلى موافقة مستقلة.

**الحالة B — §§8.66–8.70 موجودة في `HEAD` و§8.71 جديد**

حدّد التغيير المحلي الذي يضيف §8.71، وتحقق من عدم تعديل الأقسام السابقة. لا تجهّز أي staging.

**الحالة C — الأقسام مختلطة أو توجد فروق تاريخية غير محسومة**

توقف عن اقتراح نشر الملف حتى تحديد القرار المطلوب من المالك.

لا تحذف أقسامًا ولا تعيد صياغتها ولا تدمجها بهدف اجتياز بوابة Git.

### 8.3 سلامة الأقسام التاريخية

تحقق من أن §§8.60–8.70 في النسخة المحلية مطابقة للنص الموجود في `HEAD` حيث يفترض أن تكون غير معدّلة.

استخدم مقارنة مباشرة وموثوقة بين النطاقين، ولا تعتمد على SHA-256 منفردة إذا لم تكن طريقة استخراج النص وتطبيع نهايات الأسطر والترميز مطابقة للطريقة المرجعية.

البصمة التاريخية المسجلة سابقًا هي:

`aeac035e95e242ddd149f05c6b48186d1c1f7e02ec6b43e53945a1fb09adaa54`

اعتبرها قيمة مرجعية تحتاج إلى التحقق من نطاقها وطريقة إنشائها، وليست إثباتًا تلقائيًا على تطابق المحتوى.

إذا ظهر اختلاف غير مفسّر، سجّل `ADR_HISTORICAL_SECTIONS_UNRESOLVED` وتوقف عن التوصية بنشر ADR.

- طريقة الفصل المقترحة.
- مستوى المخاطرة.
- الموافقة المطلوبة.

لا تنشئ قائمة نهائية قابلة للتنفيذ باستخدام `git add` في هذه الجولة.

لا تعتبر الملف كاملًا صالحًا للنشر لمجرد أنه مرتبط بـ CapVer.

إذا تطلب الحل فصلًا داخل ملف أو تعديلًا في ملف مشترك، اشرح طريقة الفصل والمخاطر أولًا. لا تنفّذها.

إذا كان نشر مجموعة مترابطة يتطلب توسيع النطاق، فحدّد الملفات والقرارات التي يجب مراجعتها قبل منح ذلك التفويض.

---

## 12. المرحلة العاشرة — معايير التوصية

لا تصدر `READY_FOR_COMMIT` في هذه الجولة؛ لأن Commit وPush والتعديلات وstaging خارج نطاق التفويض الحالي.

استخدم إحدى الحالات التالية:

### `DIAGNOSTIC_COMPLETE`

اكتملت المراجعة، وتم تحديد مجموعة تغييرات مقترحة ومخاطرها، ولا توجد فجوات تمنع اتخاذ قرار.

### `BLOCKED`

تعذر إثبات شرط أمان أو مراجعة ملف ضروري أو حسم فرق فعلي.

### `NEEDS_OWNER_DECISION`

يتطلب الحل اختيارًا صريحًا من المالك، مثل نشر أقسام ADR محلية إضافية، أو اعتماد مجموعة ملفات مختلطة، أو تعديل ملفات مشتركة.

لا تخلط بين نجاح الاختبارات السابقة وجاهزية النشر.

لا تضع نسبًا احتمالية غير مدعومة بالأدلة. ولا تختصر المراجعة لتلبية تقدير زمني.

## 13. التقرير النهائي المطلوب

أرسل تقريرًا عربيًا واحدًا شاملًا ومنظمًا بالأقسام التالية:

### A. الحالة النهائية

إحدى الحالات المحددة في §12.

### B. حالة Git

- المستودع.
- الفرع.
- HEAD.
- upstream.
- عدد الملفات المتعقبة المعدّلة.
- عدد الملفات غير المتعقبة.
- عدد الملفات المحذوفة.
- حالة الفهرس.
- أي اختلاف عن خط الأساس المتوقع.

### C. الأسباب الفعلية للتوقف

لكل مانع:

- الدليل.
- الملف أو الملفات المتأثرة.
- أثره على النشر.
- الإجراء المقترح.
- هل يتطلب قرارًا من المالك؟

### D. جدول مراجعة الملفات

اذكر الملفات التي روجعت فعلًا، والتصنيف والنتيجة، والملفات التي لم تكتمل مراجعتها وأسباب ذلك.

### E. ADR-023

- الأقسام الموجودة في `HEAD`.
- الأقسام المحلية الإضافية.
- سلامة الأقسام التاريخية.
- نتائج المقارنة.
- الخيار المعماري الذي يحتاج إلى اعتماد، إن وجد.

### F. حماية البيانات

- نتيجة فحص ملفات SQLite والنسخ الاحتياطية.
- هل بقي المخزن العلمي دون تعديل؟
- هل تجنبت فتح قواعد التشغيل للكتابة؟
- أي تحقق تعذر تنفيذه.

لا تدّعِ أن البصمة أو العدد قد تحققا إذا لم يتم فحصهما فعليًا.

### G. الاختبارات

- الاختبارات الموجودة التي تمت مراجعتها.
- شروط العزل.
- الاختبارات التي يمكن تشغيلها لاحقًا.
- الاختبارات التي تعذر إثبات سلامتها.

وضّح أن الاختبارات لم تُشغّل في هذه الجولة.

### H. تصميم مجموعة التغييرات

جدول بالملفات المقترحة للنشر، والملفات المستبعدة من النطاق الحالي، والتغييرات المختلطة، والاعتماد بينها.

### I. القرارات المطلوبة من المالك

اكتب الأسئلة الضرورية فقط، مع شرح سبب كل قرار والخيارات ومخاطرها.

### J. تأكيدات التنفيذ

أكد بوضوح:

- لم يُنفذ `git add`.
- لم يُنفذ Commit أو Push.
- لم يُعدّل أي ملف.
- لم يُحذف أو يُستبدل أي عمل محلي.
- لم يُستخدم `reset` أو `clean` أو `stash` أو تبديل الفرع.
- لم تُشغّل الاختبارات.
- لم تُكتب أي بيانات إلى قواعد التشغيل.
- لم يُفتح المخزن العلمي للكتابة.

لا تؤكد أي بند إلا إذا كان صحيحًا وفق التنفيذ الفعلي.

---

## 14. أمر البدء

ابدأ مباشرةً بالتحقق للقراءة فقط من حالة Git، ثم نفّذ مراحل المراجعة بالترتيب.

لا ترسل خطة تمهيدية، ولا تكرر تقارير سابقة بدلًا من فحص الحالة الحالية.

لا تنفذ تعديلًا أو staging أو اختبارًا أو أمرًا قد يكتب إلى قواعد البيانات.

إذا ظهر مانع غير محسوم، وثّقه بوضوح وتوقف عن الفحوص التي قد تتجاوزه أو تغيّر الحالة.

**النهاية المطلوبة: تقرير تشخيصي موثّق يتيح للمالك اختيار الحل، دون تغيير شجرة العمل أو الفهرس أو قواعد البيانات.**
