```powershell
git diff --cached
```

راجع كامل الـ staged diff، لا الملخص فقط.

تحقق من أن:

- كل ملف في الـ index تمت مراجعته.
- لا توجد ملفات إضافية غير مقصودة.
- لا توجد قواعد بيانات أو نسخ احتياطية أو أسرار.
- التغييرات المطابقة للمهمة فقط هي الموجودة.
- لا توجد اختلافات بين القائمة المعتمدة والـ staged diff.

إذا ظهر أي اختلاف، لا تنفذ commit. لا تستخدم reset أو restore أو أي أمر لإسقاط تغييرات المستخدم. توقف وسجّل المشكلة.

---

# 9. المرحلة I — Commit

لا تنشئ commit إلا بعد اجتياز مراجعة الـ staged diff بالكامل.

## 9.1 رسالة الالتزام

اكتب رسالة دقيقة تتطابق مع محتوى الـ staged diff.

يمكن استخدام الرسالة التالية إذا كان نطاق التغييرات الفعلي يبررها:

`feat(capver): complete CapVer persistence with 5 seats verified`

لا تستخدم وصفًا يدعي استعادة تاريخية أو تغييرًا في كود الإنتاج إذا لم يتضمن الـ diff ذلك.

إذا احتجت إلى ملف رسالة، أنشئه في مسار مؤقت لا يدخل الالتزام، وتأكد من عدم تركه ضمن قائمة الملفات المراد نشرها.

## 9.2 تنفيذ commit

نفّذ commit واحدًا باستخدام الملفات الموجودة في الـ index بعد مراجعتها.

تحقق بعد التنفيذ:

```powershell
git log --oneline -1
git show --stat --oneline HEAD
git rev-parse HEAD
git status --short --branch
```

سجّل hash الالتزام، والرسالة، والملفات والسطور المضافة والمحذوفة.

إذا فشل commit:

- توقف.
- وثّق السبب.
- لا تستخدم `--amend`.
- لا تستخدم reset.
- لا تحاول تجاوز hooks أو التحقق الأمني.

إذا نجح commit لكن ظهرت مشكلة لاحقًا، لا تُنشئ commit إضافيًا ولا تعِد كتابة التاريخ تلقائيًا.

# 10. المرحلة J — بوابة Remote قبل Push

بعد نجاح commit فقط، تحقق من:

```powershell
git remote -v
git branch -vv
git rev-parse HEAD
```

تحقق من:

- وجود remote صحيح باسم `origin`.
- أن الفرع الحالي ما زال `phase-18-m18-ai-marketing-communications`.
- أن upstream هو الفرع المقصود.
- أن الوجهة لا تشير إلى مستودع غير متوقع.
- أن الدفع لا يحتاج إلى pull أو rebase أو merge.
- أن لا حاجة إلى force push.

إذا كانت حالة remote غير واضحة أو تعذر إثبات الوجهة الصحيحة، فتوقف بعد commit وبلّغ عن `COMMITTED, NOT PUSHED`.

لا تنفذ `git pull` أو `git rebase` أو `git merge` ضمن هذه المهمة.

---

# 11. المرحلة K — Push والتحقق بعده

إذا اجتازت بوابة Remote:

نفّذ:

```powershell
git push origin phase-18-m18-ai-marketing-communications
```

لا تستخدم أي خيار force.

سجّل رمز الخروج والمخرجات.

إذا فشل push:

- توقف.
- لا تحاول تجاوز الرفض.
- لا تعِد كتابة التاريخ.
- وثّق السبب الفعلي.

إذا نجح push، تحقق من:

```powershell
git rev-parse HEAD
git rev-parse origin/phase-18-m18-ai-marketing-communications
git log origin/phase-18-m18-ai-marketing-communications --oneline -3
git status --short --branch
```

المتوقع أن يشير HEAD المحلي والفرع البعيد إلى الالتزام نفسه.

لا تعِد تنفيذ أمر قبول G5-04 ولا تكتب إلى قاعدة البيانات بعد push.

# 13. شروط التوقف النهائي

إذا فشلت أي بوابة أو بقيت غير محسومة:

1. لا تنفذ commit أو push إذا لم يحدث commit بعد.
2. إذا كان commit قد نجح بالفعل ثم فشلت بوابة Remote، لا تدفعه، ولا تعِد كتابة التاريخ.
3. لا تعدّل الملفات.
4. لا تصلح `.gitignore` تلقائيًا.
5. لا تكتب إلى قواعد البيانات.
6. لا تتجاوز أي فحص أمني.
7. قدّم تقريرًا يحدد المشكلة بدقة والخطوة الآمنة التالية.

إذا نجحت جميع البوابات، نفّذ commit ثم push دون طلب تأكيد إضافي؛ فهذا التفويض صريح في هذه المهمة.

**ابدأ الآن بفحص Git للقراءة فقط. لا ترسل خطة مسبقة. لا تنفذ staging حتى تنتهي مراجعة الـ diff والبوابات الثماني.**
