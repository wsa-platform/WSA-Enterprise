```sql

FROM information_schema.tables
WHERE table_schema = 'public'

```

```sql

    SELECT 1
    FROM information_schema.tables
    WHERE table_schema = 'public'

```

`G:\New folder (3)\wsa-render-backup-extracted\2026-09-11T22_27Z\wsa_enterprise_db`
تحقق من وجودها الفعلي ومن:
- مصدرها وتاريخها.
- صيغة النسخة.
- إصدار PostgreSQL المصدر إن أمكن إثباته.
- الجداول والبيانات التي تحتوي عليها.
- مدى اكتمالها.
- ملاءمتها كمرجع تاريخي.
- عدم افتراض أنها تمثل الحالة الحالية.
ابحث عن نسخ أحدث، إن وجدت، دون إنشاء نسخة أو نقلها أو استبدالها.
## 7.1 اختلاف إصدارات PostgreSQL
سجّل الإصدارات الفعلية التي تثبتها الأدلة، مع توضيح أن التقارير السابقة ذكرت:
- Docker PostgreSQL: `16.14`.
- Render backup source: `18.4`.
- Windows PostgreSQL سابقًا: `17.11`.
لا تفترض أن خدمة Windows القديمة لا تزال موجودة أو أن بياناتها حُذفت دون دليل.
لا تنفّذ:
- `pg_restore` على قاعدة التطبيق.
- Restore من Render إلى Docker.
- ترقية PostgreSQL.
- تحويل النسخة إلى صيغة أخرى.
- أي تعديل على قاعدة البيانات أو الحاويات.
اعتبر توافق مصدر النسخة وهدفها عائقًا يجب حسمه قبل أي خطة استعادة. لا توصِ باستعادة النسخة التاريخية إلى PostgreSQL 16.14 مباشرة دون تحليل توافق موثق واختبار معزول وموافقة منفصلة.
## 7.2 معيار النسخة الاحتياطية المعتمدة
قبل أي تغيير دائم لاحقًا، يجب أن تكون النسخة:
1. من قاعدة البيانات الصحيحة.
2. حديثة ومناسبة زمنيًا للتغيير.
3. محفوظة في مسار معروف.
4. موثقًا حجمها وتاريخها وبصمة تحققها.
5. مفحوصة بأداة مناسبة لصيغتها.
6. قابلة للاستعادة عمليًا في بيئة معزولة عند الإمكان.
7. موثقة في سجل المهمة أو ADR.
8. مرتبطة بخطة استعادة لا تستبدل القاعدة الحية ولا تفقد بيانات أحدث.
لا تعتبر حجمًا معينًا، مثل 100 MB، دليلًا على سلامة النسخة أو اكتمالها.
نجاح `pg_restore --list` وحده لا يثبت إمكانية الاستعادة الكاملة.
إذا تعذر إثبات سلامة النسخة وقابليتها للاستعادة أو تعذر تحديد قاعدة البيانات الصحيحة، فلا تنفّذ أي Migration أو Restore أو تغيير دائم.
لا تنشئ نسخة احتياطية جديدة في هذه المهمة؛ المطلوب مراجعة النسخ الموجودة وتحديد الجاهزية والفجوات.

# 8. مراجعة ADR-023 والعقود المعمارية
راجع خصوصًا:
- §8.16 المتعلق بتصميم Cap Store.
- §8.58 المتعلق بتعليق Migration.
- §8.59 المتعلق باستعادة التشغيل.
- أي أقسام تتعلق بـ Identity Binding وIntegration Classification وDurable Correlation وScientific Source Record Store.
حدد:
- القرارات المعتمدة.
- التنفيذ الموجود فعلًا.
- التنفيذ غير المكتمل.
- التناقضات بين ADR والكود والمخطط.
- أي قرار سابق يشرح سبب التأجيل.
- أي تغييرات تحتاج قرار مالك المشروع.
لا تعدّل ADR-023 ولا تنشئ قرارًا معماريًا جديدًا أثناء هذه المهمة.

# 9. اختبارات السلامة والسلوك
اكتشف الاختبارات المتعلقة بـ:
- CapVer وCapability Store.
- Persistence و`STORE_UNAVAILABLE`.
- Identity Binding.
- Integration Classification.
- Durable Correlation.
- Scientific Record Store.
- LocalIndex وFTS.
- الاستمرارية بعد إعادة التشغيل.
- التوافق بين PostgreSQL وSQLite عند وجود تكامل فعلي.
قبل تشغيل أي اختبار:
1. افحص إعدادات الاختبار وقاعدة البيانات المستهدفة.
2. أثبت أن الاختبار لا يتصل بقاعدة التطبيق الحية.
3. أثبت أنه لا يشغّل Migrations أو Seeders أو Backfills غير معزولة.
4. أثبت أنه لا يعدّل ملفات البيانات الحالية.
5. إذا تعذر إثبات العزل، فلا تشغّله.
إذا كانت PHP أو أدوات الاختبار غير متاحة، لا تثبّتها ولا تغيّر البيئة. سجّل الاختبارات التي تعذّر تشغيلها وأسباب ذلك.
لا تدّعِ نجاح اختبار لم يتم تشغيله.

# 10. تصنيف المخاطر والأولويات
صنّف النتائج إلى:
- `P0` — خطر مباشر مثبت على سلامة البيانات أو النظام.
- `P1` — مسار أساسي غير متاح أو شرط أساسي غير مستوفى.
- `P2` — فجوة توافق أو استمرارية أو اعتماديات غير مكتملة.
- `P3` — تحسين توثيق أو اختبار أو صيانة.
- `UNRESOLVED` — الأدلة غير كافية.
لكل مشكلة، وثّق:
- الدليل.
- الملف والسطر أو الجدول والاستعلام.
- التأثير الفعلي المثبت.
- التأثير المحتمل غير المثبت.
- الاعتماديات.
- المخاطر.
- الحل المقترح.
- اختبارات القبول.
- شروط السماح بالتنفيذ.
- خطة التراجع.
ميّز بين:
- `CONFIRMED`
- `INFERRED`
- `UNRESOLVED`
- `NOT TESTED`
لا تصنّف المشكلة على أنها خطر مؤكد اعتمادًا على التخمين.

# 11. خطة الإصلاح المتكاملة
بعد إكمال التحقيق، أعد خطة إصلاح مرتبة حسب الاعتماديات، تشمل بحسب الأدلة:
1. معالجة أي مشكلة مثبتة في `.env`، مع اقتراح مستقل لا تنفّذه.
2. إثبات مصدر اتصال Laravel الفعلي.
3. إثبات قاعدة PostgreSQL والـ Volume اللذين يستخدمهما التطبيق.
4. تحديد ترتيب Migrations أكتوبر.
5. حسم ما إذا كانت Migration الخاصة بـ CapVer مستقلة وآمنة أو تعتمد على تغييرات أخرى.
6. تحديد حالة Identity Binding وIntegration Classification وDurable Correlation.
7. تحديد مصير Migration غير المتتبعة الخاصة بـ Scientific Store دون تعديلها.
8. تحديد الفجوات في Scientific Persistence وLocalIndex.
9. مراجعة النسخ الاحتياطية ومدى جاهزيتها.
10. تحديد اختبارات القبول قبل أي إصلاح وبعده.
11. تحديد خطة التراجع لكل تغيير.
12. تحديد ما يحتاج موافقة منفصلة من مالك المشروع.
لا تقترح تطبيق جميع Migrations دفعة واحدة إلا إذا أثبت تحليل الاعتماديات أن ذلك مطلوب وآمن.
لا تقترح إنشاء جدول يدويًا بدل Migration Laravel دون مبرر معماري موثق.
لا تغيّر التصميم المعماري لتجاوز مشكلة مخطط دون الرجوع إلى ADR-023.

# 12. قائمة الممنوعات النهائية
- لا `php artisan migrate`.
- لا `migrate:fresh`.
- لا `db:seed`.
- لا DDL أو DML.
- لا `CREATE` أو `ALTER` أو `DROP` أو `TRUNCATE` أو `INSERT` أو `UPDATE` أو `DELETE`.
- لا Restore أو `pg_restore` إلى قاعدة التطبيق.
- لا Docker start/stop/restart/rm/up/down/recreate.
- لا تعديل `.env` أو كلمات المرور.
- لا حذف أو نقل أو إعادة تسمية ملفات WIP.
- لا تعديل أو حذف ملفات غير متتبعة.
- لا Commit أو Push أو Reset أو Clean أو Stash.
- لا تعديل ADR أو العقود المعتمدة.
- لا Harvest أو Reindex أو Backfill.
- لا كشف الأسرار أو Connection Strings.
- لا الادعاء بنجاح فحص أو اختبار دون دليل.
إذا اكتشفت مشكلة جديدة أثناء التحقيق، وثّقها ولا تصلحها تلقائيًا.

# 13. التقرير النهائي الإلزامي
قدّم تقريرًا واحدًا باللغة العربية، يتضمن:
## A. الملخص التنفيذي
الحالة الفعلية وأهم النتائج والمخاطر المثبتة.
## B. سلامة البيئة
حالة `.env`، مصادر الاتصال، وأي قيود على الفحوص.
## C. هوية قاعدة البيانات
الحاوية الفعلية، الـ Volume، قاعدة البيانات، وإثبات الاتصال.
## D. مصفوفة Migrations
حالة كل Migration واعتمادياتها ومخاطرها وترتيبها المقترح.
## E. تحليل CapVer
سبب غياب الجدول وأثره الفعلي وسلوك الفشل والاختبارات.
## F. تحليل Scientific Persistence
الفصل بين PostgreSQL وSQLite والمخازن الأخرى.
## G. الملفات غير المتتبعة
الحالة والأصل المحتمل والاعتماديات والقرار المطلوب من المالك.
## H. النسخ الاحتياطية وتوافق الإصدارات
المصادر المتاحة وصلاحيتها وحدود الاستعادة الآمنة.
## I. الاختبارات
ما تم تشغيله فعليًا ونتائجه، وما تعذّر تشغيله وسبب ذلك.
## J. خطة الإصلاح
خطوات مرتبة حسب الاعتماديات، مع شروط البدء والتوقف والتراجع.
## K. معايير القبول
شروط قابلة للتحقق لإغلاق كل مشكلة.
## L. بوابة الموافقة
كل تغيير يحتاج موافقة منفصلة، ومخاطره، وما يلزم قبل تنفيذه.
## M. تأكيد السلامة
أكّد ما إذا كانت:
- قاعدة البيانات قد بقيت دون تغيير.
- الحاويات قد بقيت دون تغيير.
- ملفات `.env` قد بقيت دون تغيير.
- الملفات المحلية وغير المتتبعة قد بقيت دون تغيير.
- Git لم يشهد Commit أو Push أو عمليات تنظيف.
لا تدّعِ أن أي عنصر بقي دون تغيير إلا إذا كان ذلك متحققًا من الأدلة المتاحة.
---
# 14. شرط إنهاء المهمة
نفّذ الفحوص الآمنة المصرح بها، ثم سلّم التقرير وخطة الإصلاح.
**توقف قبل أي تغيير دائم في قاعدة البيانات أو البيانات أو ملفات الإعدادات أو حالة الخدمات.**
لا تعتبر المهمة منتهية لمجرد اكتشاف جدول CapVer المفقود. المطلوب تشخيص جميع الفجوات ذات الصلة، وتحديد أسبابها المثبتة واعتمادياتها ومخاطرها وخطة إصلاح قابلة للتحقق والتراجع.
انتظر مراجعة التقرير وموافقة مالك المشروع قبل تنفيذ أي إصلاح دائم.
