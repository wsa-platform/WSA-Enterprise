حدّد الصلاحيات المطلوبة من الكود الفعلي ومن دور التنفيذ:
- دور migrations قد يحتاج إلى إنشاء الجداول أو تعديلها.

لا تمنح صلاحيات لا تحتاجها العملية الفعلية.
## 6.3 أمثلة توضيحية للصلاحيات
الأمثلة التالية ليست أوامر تنفيذ تلقائي؛ تُستخدم فقط بعد إثبات الحاجة والتحقق من الدور والقاعدة والـ schema والموافقة على التغيير.
### مثال: صلاحيات schema
إذا ثبت أن الدور `wsa` يحتاج إلى إنشاء جداول داخل `public`:
```sql
GRANT USAGE, CREATE ON SCHEMA public TO wsa;
```
### مثال: صلاحيات الجداول الموجودة
إذا أثبت فحص الكود أن التطبيق يحتاج إلى هذه العمليات على جميع الجداول الموجودة في `public`:
```sql
GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA public TO wsa;
```
### مثال: صلاحيات التسلسلات الموجودة
إذا ثبت أن التطبيق يحتاج إلى استخدام التسلسلات:
```sql
GRANT USAGE, SELECT
ON ALL SEQUENCES IN SCHEMA public TO wsa;
```
قد تمنح هذه الأمثلة صلاحيات أوسع من المطلوب. فضّل المنح على الكائنات المحددة متى أمكن، ولا تطبقها بصورة شاملة إذا لم تكن ضرورية.

لا تستخدم `ALTER DEFAULT PRIVILEGES` تلقائيًا.
أضفه فقط إذا أثبت الفحص أن الكائنات المستقبلية التي سينشئها دور محدد تحتاج إلى صلاحيات افتراضية.
يجب مراعاة أن:
- default privileges لا تعدّل صلاحيات الكائنات الموجودة.
- إعداداتها مرتبطة بالدور الذي ينشئ الكائنات.
- يجب تحديد الـ schema المستهدف.
- لا ينبغي منح صلاحيات مستقبلية واسعة دون حاجة مثبتة.
## 6.5 بوابة الصلاحيات
قبل أي تغيير للصلاحيات، وثّق:
1. الدور المستهدف.
2. قاعدة البيانات والـ schema.
3. الصلاحيات الحالية.
4. الصلاحيات المطلوبة فعليًا.

1. تحقق من أن إنشاء الدور ضروري ومسموح به ضمن التفويض الحالي.
2. إذا كان الإنشاء ضمن التفويض، أنشئ الدور دون تضمين كلمة المرور في نص SQL.
3. عيّن كلمة المرور باستخدام `\password wsa` في جلسة `psql` تفاعلية.
4. حدّث `DB_PASSWORD` في ملف البيئة الذي يستخدمه Laravel فعليًا، بحيث يطابق كلمة المرور التي عُيّنت للدور الجديد.
5. احمِ ملف البيئة من الوصول غير المصرح به، ولا تطبع كلمة المرور أو تحفظها في سجل.
6. تحقق من أن Laravel يحمّل الإعداد الجديد، مع مراعاة config cache.
7. اختبر اتصال Laravel الفعلي وفق §8.0.
8. لا تنتقل إلى migrations أو CapVer قبل نجاح الاتصال والتحقق من هوية قاعدة البيانات والمستخدم.
مثال إنشاء الدور، عند استيفاء شروط التفويض:
```sql
CREATE USER wsa;
```
ثم في جلسة `psql` التفاعلية:
```text
\password wsa
```
إذا لم يكن إنشاء الدور أو تعديل ملف البيئة ضمن التفويض، سجّل `BLOCKED` وحدد الإجراء المطلوب والموافقة اللازمة. عدم وجود الدور لا يمنح تفويضًا تلقائيًا لتغييرات أخرى.
## 6.6.3 إذا كان الدور موجودًا والمصادقة تفشل
1. تحقق من صحة المضيف والمنفذ واسم قاعدة البيانات واسم الدور.
2. تحقق من ملف البيئة الفعلي والإعدادات المحمّلة في Laravel.
3. افحص حالة config cache دون مسحها تلقائيًا.
4. استبعد أخطاء إعدادات الاتصال وصلاحيات الوصول قبل تقرير أن كلمة المرور غير متطابقة.
5. إذا ثبت أن كلمة المرور غير متطابقة، اطلب الموافقة قبل تغيير كلمة مرور الدور الموجود.
6. إذا لم تتوفر الموافقة، أوقف مسار تغيير كلمة المرور وسجّل:
   `BLOCKED — awaiting approval to rotate wsa password`
7. لا تحاول تجاوز المصادقة أو إنشاء دور بديل لتجنب طلب الموافقة.
## 6.6.4 خطوات التنفيذ بعد الموافقة على تغيير كلمة المرور
بعد الحصول على الموافقة الصريحة:
1. استخدم `\password wsa` في جلسة `psql` تفاعلية آمنة.
2. حدّث `DB_PASSWORD` في ملف البيئة الذي يقرأه Laravel فعلًا، بحيث تتطابق القيمة مع كلمة المرور الجديدة.
3. لا تضع السر في سطر الأوامر أو سجل التنفيذ أو التقرير.
4. احمِ ملف البيئة من الوصول غير المصرح به. لا تنشئ نسخة احتياطية مكشوفة من الملف؛ وإذا تطلبت سياسة المشروع نسخة احتياطية، فاستخدم آلية محمية ومعتمدة.
5. تحقق من أن إعداد Laravel الفعلي يطابق التغيير، دون طباعة كلمة المرور.
6. إذا كان Laravel يستخدم إعدادات مخزنة مؤقتًا، فحدّد طريقة إعادة تحميلها الآمنة قبل تنفيذ أي أمر لمسحها أو تجديدها.
7. اختبر الاتصال وفق §8.0.
8. افحص الأمر `scientific:diagnose-persistence` وتأكد من وجوده وسلامة تشغيله، ثم نفّذه إذا كان مناسبًا وآمنًا.
9. لا تنتقل إلى migrations أو CapVer قبل نجاح الاتصال واجتياز الفحوص المطلوبة.
10. وثّق أن `DB_PASSWORD` تم تحديثه دون تسجيل قيمته.
## 6.6.5 شروط الإغلاق
لا تعتبر استعادة المصادقة مكتملة إلا بعد إثبات:
- الدور الصحيح.
- قاعدة البيانات الصحيحة.
- نجاح اتصال Laravel الفعلي.
- تحميل الإعدادات الجديدة.
- عدم كشف الأسرار.
- توثيق أي تغييرات أُجريت.
نجاح الاتصال لا يثبت وحده صحة صلاحيات الجداول أو نجاح CapVer أو القراءة المستقلة.

# 7. Migration المطلوبة
## 7.1 فحص migration
افحص الملف:
`backend/database/migrations/2026_10_09_140000_create_cghia_capability_cell_records_table.php`
تحقق من:
- أسماء الأعمدة وأنواعها.
- المفاتيح الأساسية والفريدة.
- الفهارس.
- القيود.
- استخدام serial أو identity أو sequences.
- عمليات `up()` و`down()`.
- ما إذا كان الجدول موجودًا بالفعل.
- سجل Laravel الخاص بالـ migrations.
- أي تغييرات غير متوافقة مع الجداول الموجودة.
## 7.2 فحص قبل التنفيذ
استخدم `--pretend` إذا كان إصدار Laravel وأمر migration يدعمان ذلك، بعد فحص المساعدة.
مثال توضيحي:
```powershell
php artisan migrate --pretend --path=database/migrations/2026_10_09_140000_create_cghia_capability_cell_records_table.php
```
شغّل الأمر من مجلد `backend`.
هذا الفحص لا يضمن أن التنفيذ الفعلي سينجح، ولا يعوّض فحص حالة قاعدة البيانات.
## 7.3 شروط التنفيذ
لا تنفّذ migration إلا إذا:
- اتصل Laravel بقاعدة البيانات الصحيحة.
- ثبت أن migration مطلوبة وغير مسجلة.
- فُحص الجدول الحالي ولم تظهر تعارضات.
- كانت الصلاحيات كافية.
- لم تتطلب العملية حذفًا أو استبدالًا أو تغييرًا غير مصرح به.
إذا كان الجدول موجودًا لكن migration غير مسجلة، فلا تحاول تجاوز المشكلة بإعادة إنشاء الجدول. افحص الحالة واطلب قرارًا إذا لم يوجد مسار آمن ومثبت.
## 7.4 أمر التنفيذ المشروط
بعد استيفاء الشروط السابقة، يمكن تنفيذ migration المحددة وحدها:
```powershell
php artisan migrate --path=database/migrations/2026_10_09_140000_create_cghia_capability_cell_records_table.php
```
لا تستخدم `migrate:fresh` أو rollback أو أي إجراء شامل.
بعد التنفيذ، تحقّق من:
- نتيجة الأمر الفعلية.
- وجود الجدول.
- الأعمدة والفهارس والقيود.
- سجل migrations.
- القدرة على قراءة الجدول من اتصال Laravel.
إذا تعذر تشغيل PHP أو لم يتوفر اتصال صالح، فلا تدّعِ نجاح migration.

# 8. التشخيص والتحقق من الاتصال
## 8.0 اختبار اتصال Laravel بإعداداته المحمّلة فعليًا
فضّل اختبارًا يستخدم اتصال Laravel الافتراضي نفسه، بدل إنشاء اتصال منفصل لا يعكس إعدادات التطبيق.
`DB::connection()->getPdo()` مناسب لفتح اتصال فعلي. ويمكن استخدام استعلام هوية الجلسة لتحديد قاعدة البيانات والمستخدم اللذين يتصل بهما Laravel.
المثال التالي توضيحي فقط:
```php
<?php
// backend/test_connection.php
// مثال توضيحي — لا تنشئ الملف قبل فحص Git/WIP.
require __DIR__ . '/vendor/autoload.php';
$app = require_once __DIR__ . '/bootstrap/app.php';
$app->make(
    \Illuminate\Contracts\Console\Kernel::class
)->bootstrap();
try {
    $connection = \Illuminate\Support\Facades\DB::connection();
    $connection->getPdo();
    $identity = $connection->selectOne(
        'SELECT current_database() AS database_name,
                current_user AS session_user'
    );
    echo "CONNECTED\n";
    echo "DATABASE: " . $identity->database_name . PHP_EOL;
    echo "SESSION_USER: " . $identity->session_user . PHP_EOL;
    echo "DRIVER: " . $connection->getDriverName() . PHP_EOL;
} catch (\Throwable $e) {
    // لا تطبع رسالة الاستثناء كاملة؛ فقد تتضمن معلومات حساسة.
    echo "FAILED: " . get_class($e) . PHP_EOL;
    exit(1);
}
```
### شروط استخدام المثال
1. افحص إصدار Laravel وطريقة تهيئة التطبيق قبل اعتماد المثال.
2. لا تنشئ الملف قبل فحص `git status` والملفات الموجودة.
3. إذا قررت إنشاء الملف، سجّل أنه ملف جديد ضمن تغييرات WIP.
4. شغّله من مجلد `backend` فقط بعد التأكد من المسارات.
5. لا تطبع كلمة المرور أو سلسلة الاتصال أو الأسرار.
6. لا تعرض رسالة الاستثناء كاملة في تقرير قد يُشارك.
7. نجاح `CONNECTED` يثبت فتح الاتصال والاستعلام، لكنه لا يثبت صلاحيات CapVer أو نجاح الكتابة الدائمة.
8. إذا تعذر إنشاء ملف دون المساس بملف موجود، استخدم اختبار Laravel أو أداة تشخيص موجودة، إن كانت متاحة وآمنة.
## 8.1 بدائل الاختبار
إذا لم يكن الاختبار المستقل مناسبًا، استخدم بالترتيب:
1. اختبار Laravel موجودًا بالفعل ومخصصًا لاتصال قاعدة البيانات.
2. أداة تشخيص موجودة تدعم التحقق من الاتصال الفعلي.
3. اختبار PDO مستقل فقط إذا كان متوافقًا مع الهدف ومُعدًا بطريقة لا تكشف الأسرار.
لا تستخدم اختبارًا لا يعكس إعدادات التطبيق ثم تعتبره دليلًا على نجاح Laravel.
## 8.2 اختبارات التشخيص الموجودة
افحص المساعدة الفعلية للأوامر المعروفة:
```powershell
php artisan scientific:diagnose-persistence --help
php artisan scientific:capver-accepted --help
php artisan scientific:ensure-record-store --help
php artisan scientific:reconcile-record-store --help
```
إذا لم يدعم الأمر `--help`، افحص تعريف الأمر في الكود بدل افتراض سلوكه.
لا تنفّذ أمرًا قد يكتب بيانات أو يغيّر حالة المخزن قبل فحص سلوكه.
## 8.3 فصل نتائج الاختبارات
سجّل كل نتيجة بصورة منفصلة:
- اتصال TCP/جاهزية الخادم.
- مصادقة PostgreSQL.
- اتصال Laravel.
- هوية قاعدة البيانات والمستخدم.
- صلاحيات schema.
- وجود الجدول.
- إمكانية القراءة.
- إمكانية الكتابة.
- القراءة المستقلة بعد الكتابة.
نجاح أي مرحلة لا يعني نجاح المراحل التالية.

# 9. CapVer والقراءة المستقلة وGBIF
## 9.0 التحقق من CapVer
افحص مسار CapVer الفعلي، بما فيه:
- مصدر بيانات القرار.
- شروط قبول القدرة.
- شروط `persistCurrent`.
- سلوك `ALREADY_CURRENT`.
- معنى الحالات التي يعيدها المسار.
- طريقة تخزين السجل.
- طريقة قراءة السجل بعد الكتابة.
لا تغيّر العقد أو شروط القبول بهدف جعل الاختبار ينجح.
## 9.0.1 معيار كفاية فحص Tinker
لا تستخدم Tinker لاستدعاء خدمة CapVer أو `persistCurrent` قبل استيفاء المعايير التالية.
### المعيار الأول: توقيع الدالة العامة
اقرأ تعريف الدالة العامة وتحقق من:
- المعاملات المطلوبة.
- أنواع المعاملات.
- القيمة المعادة.
- الاستثناءات أو الأخطاء المعروفة.
- أي متطلبات مسبقة موثقة.
### المعيار الثاني: عقد CapVer ومسار الاستدعاء
اقرأ العقد الذي يحدد كيفية استدعاء `persistCurrent`، ثم تتبع المسار الفعلي الذي يصل إليه.
يجب معرفة:
- كيف يُنشأ القرار أو السجل المدخل.
- ما الشروط التي تسمح بالكتابة.
- كيف يُحدد السجل الحالي.
- كيف تُفسر حالة `ALREADY_CURRENT`.
- ما الذي يجعل النتيجة مقبولة أو مرفوضة.
لا يكفي وجود الدالة أو توقيعها وحده.
### المعيار الثالث: الآثار الجانبية
افحص الآثار الجانبية المباشرة وغير المباشرة ذات الصلة، ومنها:
- عمليات الكتابة إلى قاعدة البيانات.
- الجداول الأخرى التي قد تتأثر.
- المعاملات.
- الأحداث أو المستمعات أو الوظائف التي تُستدعى.
- أي تغييرات في الحالة أو آثار لا يمكن التراجع عنها بأمان.
لا يشترط عدد ثابت من الملفات؛ يجب فحص كل جزء لازم لإثبات سلامة المسار.
### المعيار الرابع: شروط التشغيل
تحقق من:
- أن المدخلات متاحة وصحيحة.
- أن الاتصال يشير إلى قاعدة البيانات الصحيحة.
- أن الاستدعاء لا يتجاوز المسار الرسمي.
- أن العملية ضمن التفويض.
- أن سلوك التكرار مفهوم.
- أن الاختبار لا يغيّر بيانات حقيقية غير مصرح بها.
### قرار السماح باستخدام Tinker
- إذا تحققت المعايير وكان الاستدعاء آمنًا ومصرحًا به، يمكن استخدام Tinker وفق الطريقة التي يحددها الكود.
- إذا بقي شرط جوهري غير محسوم، لا تستدعِ الخدمة، وسجّل `NOT_VERIFIED`.
- لا تخترع أسماء methods أو arguments أو كائنات اختبار.
- لا تنفّذ استدعاءً لمجرد إكمال قائمة الاختبارات.
## 9.1 اختبار الكتابة والقراءة المستقلة
يجب التمييز بين:
1. نجاح الاستدعاء داخل العملية الحالية.
2. وجود سجل في قاعدة البيانات.
3. قدرة اتصال مستقل على قراءة السجل نفسه.
إذا كان مسار الكتابة مدعومًا وآمنًا ومصرحًا به:
- استخدم سجلًا اختباريًا محددًا ومناسبًا وفق عقد النظام.
- لا تعدّل سجل إنتاج قائمًا.
- لا تحذف سجلات موجودة.
- سجّل هوية السجل ومفتاح التحقق غير السري.
- افتح اتصالًا جديدًا أو عملية جديدة حسب البنية الفعلية.
- اقرأ السجل من مخزن PostgreSQL نفسه.
- تحقق من تطابق هوية السجل والحقول اللازمة لإثبات النتيجة.
- وثّق ما إذا كانت القراءة المستقلة قد نجحت.
إذا لم تتوفر طريقة آمنة لإنتاج سجل اختباري أو لم يكن الاستدعاء مدعومًا، لا تخترع مسارًا بديلًا. سجّل `NOT_VERIFIED` أو `BLOCKED` بحسب السبب.
## 9.2 Idempotency
تحقّق من سلوك تكرار العملية وفق العقد الفعلي.
لا تفترض أن `ALREADY_CURRENT` يساوي دائمًا `PERSISTED` في كل سياق. وثّق المعنى المحدد في الكود وشروط قبول النتيجة.
لا تكرر الكتابة في قاعدة البيانات لمجرد إثبات idempotency إذا كان التكرار قد يغير حالة أو ينشئ سجلات إضافية.
## 9.3 GBIF
لا تفترض أن GBIF مشمول في مجموعة CapVer الافتراضية.
افحص:
- سجل المصادر الفعلي.
- عقد القدرات.
- أوامر التشخيص المدعومة.
- الشروط المطلوبة لتفعيل المصدر.
- ما إذا كان مسار التحقق يسمح باختبار GBIF دون تغيير غير مصرح به.
إذا لم يكن هناك مسار مدعوم، فلا تخترع أمرًا أو استدعاء Tinker. سجّل الحالة `NOT_VERIFIED` أو `BLOCKED` وفق السبب.
لا تعتبر وجود GBIF في Registry دليلًا على تفعيله أو نجاح تخزين قدراته.

# 10. بوابات القبول المتسلسلة
يجب اجتياز البوابات بالترتيب. لا تتجاوز بوابة فاشلة لإكمال ما بعدها.
## Gate A — سلامة المشروع
الشروط:
- تحديد الفرع وHEAD الحاليين.
- تسجيل حالة Git وWIP.
- تحديد ملفات الاختبار والتغيير المحتملة.
- التأكد من عدم تنفيذ أوامر مدمرة.
النتيجة المقبولة: `VERIFIED` إذا جُمعت الأدلة فعلًا.
إذا تعذر إثبات حالة المشروع: `BLOCKED`.
## Gate B — اتصال PostgreSQL
الشروط:
- PostgreSQL متاح.
- المضيف والمنفذ صحيحان من بيئة Laravel.
- قاعدة البيانات موجودة.
- الدور وبيانات الاعتماد صالحان.
- لا توجد أسرار مكشوفة.
نجاح اتصال إداري وحده لا يكفي.
## Gate C — اتصال Laravel والصلاحيات
الشروط:
- Laravel يتصل بقاعدة البيانات المقصودة.
- هوية الجلسة موثقة.
- الصلاحيات اللازمة مثبتة.
- لا توجد تغييرات صلاحيات غير مبررة.
## Gate D — Migration والجدول
الشروط:
- migration مفحوصة.
- حالة الجدول الحالية معروفة.
- لم يُستخدم أي إجراء هدّام.
- migration المحددة نُفذت فقط عند استيفاء الشروط.
- البنية الفعلية مطابقة لما يتطلبه الكود.
## Gate E — CapVer والقراءة المستقلة
الشروط:
- عقد الاستدعاء مفحوص.
- الكتابة تمت عبر مسار مدعوم وآمن ومصرح به، إذا أمكن.
- القراءة المستقلة أثبتت وجود السجل نفسه.
- حالات النجاح والتكرار مفسرة وفق الكود.
- لا يوجد ادعاء بالنجاح عند غياب دليل.
## Gate F — التوثيق والإغلاق
الشروط:
- توثيق الأدلة والنتائج.
- تحديث ADR-023 بإضافة ملحق جديد دون حذف المحتوى السابق.
- إعداد التقرير النهائي بالعربية.
- التوقف قبل Commit أو Push.
اجتياز Gate F يعني اكتمال التقرير المصرح به، ولا يعني تلقائيًا أن المشروع أصبح `PRODUCTION_READY` أو `FULL_SCOPE_COMPLETE`.

# 11. القيود الهندسية الإضافية
## 11.1 لا تغيّر المعمارية
لا تعدّل:
- هوية السؤال العلمي.
- عقد CSQ.
- مسار البحث العلمي.
- Source Registry.
- Capability Contract.
- منطق LocalIndex.
- منطق ترتيب النتائج.
- سياسات الأدلة العلمية.
إلا إذا ثبت أن التغيير ضروري ومصرح به صراحةً. أي حاجة خارج النطاق تُسجّل كعمل لاحق.
## 11.2 عدم خلط المخازن
لا تعتبر:
- نجاح SQLite دليلًا على نجاح PostgreSQL.
- نجاح PostgreSQL دليلًا على نجاح Laravel.
- نجاح Laravel دليلًا على نجاح CapVer.
- وجود سجل في الذاكرة دليلًا على استمراره بعد انتهاء العملية.
- `contract_verified` دليلًا على `CAPABILITY_PERSISTED`.
- نجاح مصدر واحد دليلًا على نجاح جميع المصادر.
## 11.3 الاختبارات
شغّل الاختبارات التي تسمح بها البيئة والنطاق فقط.
قبل تشغيل أي اختبار:
- افحص هل يكتب إلى قاعدة البيانات.
- تحقق من أنه لا يحذف بيانات.
- حدد إن كان يحتاج إلى قاعدة اختبار منفصلة.
- لا تستخدم قاعدة الإنتاج أو قاعدة التطوير القائمة لاختبارات تدميرية.
- لا تدّعِ نجاح اختبار لم يُشغّل.
إذا لم يكن PHP متاحًا، لا تستخدم Docker كبديل، ولا تصف الاختبارات بأنها ناجحة. سجّل القيود بدقة.

# 13. التقرير الهندسي النهائي
اكتب التقرير النهائي بالعربية، بصورة شاملة ومركزة، دون تكرار تحليلات متعددة لنفس النتيجة.
## 13.1 الملخص التنفيذي
اذكر:
- الحالة الإجمالية.
- ما تم إصلاحه فعليًا.
- ما ثبت نجاحه.
- ما بقي معطلًا.
- ما إذا كانت هناك حاجة إلى موافقة إضافية.
## 13.2 جدول النتائج
استخدم الحالات التالية فقط عند انطباقها:
- `VERIFIED`: تم التحقق بدليل مباشر في التنفيذ الحالي.
- `REPORTED_NOT_RECHECKED`: معلومة تاريخية لم تُعَد مراجعتها.
- `PENDING`: خطوة لم تُنفذ بعد.
- `BLOCKED`: تعذر التنفيذ بسبب شرط أو صلاحية أو اعتماد غير متوفر.
- `NOT_VERIFIED`: لا توجد أدلة كافية لإثبات النتيجة.
لا تستخدم `VERIFIED` لمجرد أن الأمر بدا صحيحًا أو أن تقريرًا سابقًا قال إنه نجح.
## 13.3 أدلة قابلة للمراجعة
لكل نتيجة مهمة، اذكر:
- الأمر أو الفحص الذي نُفذ.
- النتيجة الفعلية بعد تنقيح الأسرار.
- الملف أو المسار المعني.
- أي قيود تؤثر في الاستنتاج.
- ما إذا كان الاختبار قد غيّر بيانات.
لا تضع كلمات المرور أو مفاتيح API أو أسرار البيئة في التقرير.
## 13.4 الملفات المتغيرة
اعرض قائمة واضحة بالملفات التي تغيرت أثناء المهمة، مع سبب كل تغيير.
ميّز بين:
- ملفات كانت متغيرة مسبقًا.
- ملفات عدّلها التنفيذ الحالي.
- ملفات جديدة.
- ملفات لم تُعدّل.
## 13.5 حالة الإغلاق
يجب أن ينتهي التقرير بتحديد:
- آخر بوابة اجتازت التحقق.
- أول بوابة لم تُجتز، إن وجدت.
- ما إذا كان CapVer قد ثبت نجاح تخزينه وقراءته مستقلًا.
- ما إذا كانت GBIF قد تحققت أم لا.
- هل بقيت موافقات مطلوبة.
- التأكيد أن Commit وPush لم يُنفذا.
لا تعلن اكتمال النطاق بالكامل إذا بقي أي شرط قبول غير مثبت.

# 15. أمر البدء
ابدأ الآن بالتنفيذ الفعلي داخل بيئة المشروع المتاحة.
الترتيب الإلزامي:
1. افحص حالة Git وWIP والفرع وHEAD.
2. افحص بيئة PHP وDrivers دون كشف الأسرار.
3. افحص إعدادات Laravel ومصدرها الفعلي.
4. افحص بنية CapVer والمستودع والـ migration.
5. شخّص اتصال PostgreSQL من بيئة Laravel الفعلية.
6. حدّد ما إذا كان الدور `wsa` موجودًا قبل اتخاذ أي إجراء متعلق بكلمة المرور.
7. إذا كان الدور غير موجود، أنشئه فقط إذا كان ذلك ضمن التفويض، ثم عيّن كلمة المرور وحدّث `DB_PASSWORD` بأمان.
8. إذا كان الدور موجودًا وفشلت المصادقة، افحص أسباب الفشل الأخرى أولًا، ولا تغيّر كلمة المرور إلا بعد الموافقة المطلوبة.
9. لا تُجرِ أي تغيير في قاعدة البيانات أو الصلاحيات أو بيانات الاعتماد قبل إثبات الحاجة واستيفاء شروط التفويض.
10. نفّذ أقل إصلاح ممكن ضمن التفويض.
11. شغّل الفحوص المسموح بها فقط.
12. تحقق من CapVer والقراءة المستقلة وفق المعايير الواردة أعلاه.
13. حدّث ADR-023 بإضافة ملحق فقط، إذا أمكن توثيق النتائج بأمان.
14. أعد التقرير الهندسي العربي النهائي.
15. توقّف قبل Commit أو Push.

- لا تكرر الفحوص التي نجحت بالفعل إلا إذا كان هناك سبب جديد أو تغير في البيئة.
- لا تخترع نتائج أو موافقات أو ملفات.
- لا تعرض الأسرار.
- لا تحذف WIP.
- لا تنفّذ Docker.
- لا تنفّذ Commit أو Push.
