# WSA-Enterprise — Forensic Git Review and Safe Commit Preparation
## الدور
تصرف كمهندس برمجيات خبير ومسؤول عن سلامة Git في مشروع WSA-Enterprise.
Repository:
`G:\WSA-Enterprise`
## الهدف
فحص جميع الملفات التي تحتوي على تغييرات لم تُسجَّل في Commit، وتحديد ما يصلح للالتزام، وفصل العمل المكتمل عن العمل غير المكتمل، ثم تجهيز مجموعة Commit آمنة ومحددة دون تنفيذ Commit أو Push.
## قواعد الحماية الإلزامية
1. لا تنفذ `git commit` أو `git push` أو merge أو rebase.
2. لا تستخدم:
   - `git reset`
   - `git clean`
   - `git restore`
   - `git stash`
3. لا تحذف أو تستبدل أو تتراجع عن أي تعديل موجود.
4. لا تستخدم `git add .` أو `git add -A` أو أي إضافة جماعية عمياء.
5. لا تضف ملفات غير متعقبة لمجرد أنها موجودة.
6. لا تعدّل كود التطبيق أو الاختبارات أثناء مرحلة الفحص والتصنيف.
7. لا تعدّل `.env` أو ملفات الأسرار أو ملفات قواعد البيانات أو النسخ الاحتياطية.
8. لا تُدخل ملفات SQLite أو PostgreSQL أو Docker volumes أو الملفات الكبيرة والبيانات المولدة في Commit دون قرار صريح.
9. حافظ على الملف غير المتعقّب:
   `backend/database/migrations/2026_10_15_220000_create_scientific_source_record_store_tables.php`
   لا تضفه إلى Commit، ولا تعدّله أو تنقله أو تحذفه؛ يحتاج إلى مراجعة واعتماد مستقلين.
10. حافظ على جميع تغييرات WIP الحالية، بما فيها التغييرات الموجودة مسبقًا في `.gitignore`.
11. لا تفترض أن كل ملف معدّل مكتمل أو أن كل ملف غير متعقّب جديد يجب إضافته.
12. إذا ظهر أي ملف حساس أو غير واضح الملكية أو الغرض، استبعده من مجموعة Commit المقترحة وسجّل سبب الاستبعاد.
13. لا تغيّر إعدادات Git أو hooks أو إعدادات المستودع لتجاوز الفحوصات.
14. لا تُعلن نجاح أي فحص لم يُنفَّذ فعليًا.
## المرحلة الأولى — جرد Git للقراءة فقط
نفّذ وسجّل نتائج:
- `git status --short`
- `git status --branch`
- `git diff --stat`
- `git diff --name-status`
- `git diff --cached --stat`
- `git diff --cached --name-status`
- `git ls-files --others --exclude-standard`
- `git diff --check`
افحص أيضًا الملفات المتجاهلة ذات الصلة فقط عند الحاجة، دون إضافة الملفات المتجاهلة تلقائيًا.
حدّد:
- الفرع الحالي وHEAD.
- الملفات المتعقبة المعدّلة.
- الملفات الجديدة غير المتعقبة.
- الملفات المحذوفة أو المعاد تسميتها.
- التغييرات الموجودة بالفعل في staging.
- أي تغييرات كانت موجودة قبل بدء هذه المهمة، إذا أمكن إثبات ذلك من السجل المتاح.
لا تعتمد على عدد الملفات وحده لتحديد النطاق؛ افحص كل مسار وتغيير ذي صلة.
## المرحلة الثانية — مراجعة محتوى التغييرات
لكل ملف مرشح، افحص diff ومحتواه ذي الصلة وصنّفه ضمن إحدى الفئات:
A. مكتمل، محدد النطاق، ومناسب للـ Commit.
B. يحتاج إلى اختبار أو تحقق إضافي قبل الالتزام.
C. عمل جارٍ أو غير مكتمل (WIP).
D. ملف حساس أو بيانات تشغيلية أو نسخة احتياطية أو ملف مولّد.
E. ملف معماري أو توثيقي يحتاج إلى مراجعة دقة الادعاءات.
F. ملف ترحيل أو تغيير بنية قاعدة بيانات يحتاج إلى اعتماد مستقل.
G. ملف لا يمكن تحديد غرضه أو سلامته بثقة.
لكل ملف، وضّح:
- المسار.
- الحالة في Git.
- ملخص التغيير.
- علاقته ببقية الملفات.
- الاختبارات المناسبة ونتائجها الفعلية، إن كانت موجودة.
- المخاطر أو الاعتماديات.
- التصنيف والسبب.
- هل يُقترح تضمينه في Commit أم استبعاده مؤقتًا.
لا تعتمد على ملخص سابق بدلًا من مراجعة الحالة الحالية.
## المرحلة الثالثة — تحليل مجموعات الالتزام
كوّن مجموعات منطقية مستقلة حسب الوظيفة، مع مراعاة الاعتماديات بين الملفات.
لا تخلط في Commit واحد تغييرات غير مترابطة، مثل:
- إصلاحات كود التطبيق.
- اختبارات مستقلة.
- تحديثات ADR.
- إعدادات بيئة التشغيل.
- ترحيلات قواعد البيانات.
- ملفات بيانات أو نسخ احتياطية.
إذا كان ملف واحد يحتوي على تغييرات مكتملة وأخرى غير مكتملة، فلا تضف الملف كاملًا عشوائيًا. افحص إمكانية فصل التغييرات بأمان، وإذا تعذر ذلك فاستبعد الملف مؤقتًا واشرح السبب.
## المرحلة الرابعة — تجهيز مرشحي Commit دون تنفيذ الالتزام
أنشئ قائمة دقيقة بالملفات المقترحة لكل مجموعة Commit.
يمكنك تجهيز staging لملفات محددة فقط بعد التأكد من محتواها وسلامتها وعدم وجود أجزاء WIP مختلطة، مع الالتزام بما يلي:
- استخدم المسارات المحددة صراحةً فقط.
- لا تستخدم الإضافة الجماعية.
- لا تدرج الملف العلمي غير المتعقّب المذكور أعلاه.
- لا تدرج قواعد البيانات أو النسخ الاحتياطية أو الأسرار.
- لا تُزل أي ملف من staging إذا كان موجودًا مسبقًا؛ لا تغيّر staging السابق دون إذن.
- إذا تعذر التمييز بين staging السابق والجديد بأمان، اكتفِ بتقديم أوامر staging مقترحة في التقرير ولا تنفذها.
إذا جهزت staging، افحص `git diff --cached` لكل مجموعة، ثم تحقّق أن محتواها يطابق القائمة المقصودة بالضبط. لا تنفذ Commit.
## المرحلة الخامسة — فحوصات ما قبل الالتزام
لكل مجموعة مرشحة:
1. حدّد الاختبارات المطلوبة بناءً على الملفات المتغيرة.
2. افحص وجود بيئة الاختبار ومتطلباتها قبل تشغيل الاختبارات.
3. شغّل الاختبارات المناسبة فقط إذا كانت آمنة ولا تكتب إلى قواعد بيانات التشغيل.
4. إذا كان الاختبار قد يلمس SQLite التشغيلية أو PostgreSQL، فلا تشغله قبل إثبات العزل.
5. لا تُصلح فشل الاختبارات تلقائيًا ضمن هذه المهمة؛ سجّل المشكلة كعنصر منفصل.
6. تحقق من عدم إدخال أسرار أو بيانات تشغيلية أو تغييرات غير مرتبطة.
7. أعد فحص حالة Git و`git diff --check`.
## التقرير النهائي — باللغة العربية
قدّم تقريرًا واحدًا شاملًا يحتوي على:
1. الفرع الحالي وHEAD.
2. عدد الملفات المتعقبة المعدّلة، وغير المتعقبة، والمحذوفة، والموجودة في staging، وفق الحالة الفعلية.
3. جدولًا كاملًا لتصنيف الملفات.
4. مجموعات Commit المقترحة، مع أسماء رسائل Commit المقترحة.
5. الملفات التي تم تجهيزها في staging فعليًا، إن وُجدت.
6. الملفات المستبعدة وأسباب الاستبعاد.
7. الاختبارات التي نُفذت ونتائجها الفعلية.
8. المشكلات أو الاعتماديات التي تمنع الالتزام الآمن.
9. نتيجة `git status --short` النهائية.
10. تأكيد عدم تنفيذ Commit أو Push.
11. أوامر Commit المقترحة لكل مجموعة، دون تنفيذها.
**معيار النجاح:** جميع تغييرات العمل معروفة ومصنفة، ولا يُدرج أي ملف في مجموعة الالتزام دون مراجعة محتواه، ولا يُفقد أي WIP، وتكون الخطوة التالية واضحة للموافقة.
توقّف بعد التقرير النهائي وانتظر موافقة صاحب المشروع.
