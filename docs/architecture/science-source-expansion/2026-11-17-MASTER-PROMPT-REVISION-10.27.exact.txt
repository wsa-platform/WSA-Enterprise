## 3.7 Ingest Lifecycle — Mandatory Operational Contract
### 3.7.1 Purpose
Every Ingest run must be observable, safely stoppable, auditable, and recoverable.
A Persistence Checkpoint alone is not a complete Ingest Lifecycle.
### 3.7.2 Run Identity
Record for every run:
- Unique Run ID.
- PID.
- Container ID, if applicable.
- Start timestamp.
- Branch.
- HEAD.
- Implementation version.
- Candidate Generation.
- Current package.
- Current Batch.
- Current Chunk.
- Last successful Commit.
- Last valid Persist checkpoint.
- FTS checkpoint, if relevant.
- Last verified progress timestamp.
Do not expose secrets or environment variable contents.
### 3.7.3 Progress Detection
Progress must be supported by persistent evidence, not console logs alone.
Track:
- Last completed package.
- Last committed Batch.
- Last completed Chunk.
- Committed persisted record count.
- Last checkpoint update.
- Last completed database transaction.
- Last durable progress marker.
Distinguish:
- `ACTIVE_PROGRESSING`
- `ACTIVE_SLOW`
- `WAITING`
- `BLOCKED`
- `STALLED`
- `FAILED`
- `GRACEFULLY_STOPPED`
- `ABNORMALLY_TERMINATED`
- `COMPLETED`
New log lines alone do not prove durable progress.
### 3.7.4 Stalled Detection
Define the stall threshold using:
- Historical throughput.
- Package size.
- Current workload.
- Last durable progress.
- Database and filesystem activity.
- Current system conditions.
Before declaring a stall:
1. Check process state.
2. Check CPU and I/O activity.
3. Check SQLite locks.
4. Check writer activity.
5. Check WAL changes.
6. Check transaction state.
7. Check the last valid checkpoint.
8. Check whether the process is waiting on another resource.
Do not terminate a process merely because no new log line appeared.
Do not use an arbitrary short inactivity threshold.
### 3.7.5 Graceful Shutdown
When a stop is required:
1. Record the reason.
2. Capture the current Run ID and process state.
3. Issue the supported application-level stop request or graceful signal.
4. Allow the current safe transaction boundary to finish.
5. Allow checkpoint persistence.
6. Close database connections and file handles correctly.
7. Verify process exit.
8. Verify checkpoint validity.
9. Verify no remaining writer.
Do not terminate the process during an active transaction simply to save time.
### 3.7.6 Graceful Shutdown Timeout
Set and document the timeout using observed behavior and approved configuration.
Timeout expiration is a diagnostic trigger, not automatic authorization for Hard Kill.
After timeout:
- Recheck process state.
- Recheck durable progress.
- Recheck transaction state.
- Recheck database locks.
- Recheck active writers.
- Preserve logs and checkpoint data.

### 3.7.7 Hard Kill Restriction
Hard Kill is the last resort.
It may be considered only when the following evidence has been captured:
1. Exact process identity and PID.
2. Exact Container identity, if applicable.
3. Graceful Shutdown request.
4. Timeout expiration.
5. Evidence graceful shutdown failed.
6. Evidence of no durable progress during the diagnosed stall interval.
7. Current transaction and database-lock state.
8. Confirmation that no other writer is active.
9. Current checkpoint.
10. Current WAL/SHM state.
11. Relevant logs.
12. Documented reason waiting is no longer viable.
13. Recovery and integrity-verification plan.
If a required critical item is unavailable:
`HARD_KILL_NOT_AUTHORIZED — INSUFFICIENT_EVIDENCE`
Do not kill an entire container or unrelated workloads.
Do not delete WAL or SHM files.
Do not delete Candidate data.
Do not discard checkpoints.
### 3.7.8 Recovery After Abnormal Exit
After abnormal termination:
1. Confirm the process has exited.
2. Confirm no other writer remains.
3. Preserve database, WAL, SHM, checkpoints, and logs.
4. Use the approved SQLite recovery/open procedure.
5. Run the appropriate integrity verification.
6. Identify the last committed Batch and Chunk.
7. Verify record identities.
8. Verify provenance.
9. Verify package completion state.
10. Resume only from the last valid committed Persist checkpoint.
If integrity is uncertain, do not resume writes.
Preserve the data and investigate.
