# القسم 2 — موافقة المالك المسبقة على القرارات
## 2.1 الموافقة الرسمية
يعلن مالك المشروع موافقته المسبقة على اتخاذ وتنفيذ القرارات المعمارية والتقنية اللازمة لإغلاق Phase 1، بما في ذلك القرارات التي كانت تتطلب سابقًا موافقة المالك، وخصوصًا:
- Gate A المرتبط بـ P1-EXIT-02.
- Gate B المرتبط بـ P1-EXIT-03.
- القرارات المعمارية التابعة لهما.
- القرارات التنفيذية اللازمة لاستكمال P1-EXIT-05.
- القرارات اللازمة لاستكمال P1-EXIT-06.
- القرارات اللازمة لاستكمال P1-EXIT-08.
- القرارات المتعلقة بالعقود والـ Adapters والتكامل.
- القرارات اللازمة لمعالجة الفجوات التي كشفها تقرير Revision 7.
هذه موافقة مالك مسبقة لتجنب تعطيل التنفيذ بسبب انتظار موافقات متكررة على القرارات الهندسية الواقعة ضمن نطاق Phase 1.
## 2.2 طريقة استخدام الموافقة
قبل حسم Gate A أو Gate B:
1. استخرج التعريف الأصلي للبوابة من ADR-023.
2. راجع القرارات السابقة المرتبطة بها.
3. افحص التنفيذ الحالي.
4. حدد المشكلة التي تمنع الإغلاق.
5. حدد البدائل المعمارية الصحيحة.
6. حلل آثار كل بديل.
7. اختر الحل الأكثر اتساقًا مع معمارية المشروع.
8. وثق أسباب الاختيار.
9. نفذ القرار.
10. أضف اختبارات تثبت صحته عند الحاجة.
11. حدث ADR-023 وسجل القرارات.
12. اربط القرار بالمعايير التي يؤثر فيها.
لا تطلب من المالك إعادة اعتماد خيار هندسي يقع ضمن نطاق هذه الموافقة.
## 2.3 حدود الموافقة
الموافقة المسبقة لا تسمح بما يلي:
- حذف قواعد البيانات التشغيلية المحمية.
- حذف السجلات التاريخية.
- إتلاف الأرشيف أو استبدال نسخه.
- إعادة كتابة Git History.
- Force Push.
- حذف WIP مجهول أو غير مراجع.
- كشف Secrets أو نقلها.
- تغيير نطاق المشروع إلى Phase 2 أو Phase 3.
- إجراء التزامات مالية أو تعاقدية خارجية.
- تغيير متطلبات تجارية أو قانونية خارج نطاق Phase 1.
- اختلاق Evidence أو مستندات تاريخية.
إذا ظهر إجراء من هذه الفئات، حافظ على البيانات وتوقف عن الإجراء المحدد فقط، ثم وثق السبب وأكمل الأعمال المستقلة.
## 2.4 عدم اختلاق القرار الأصلي
موافقة المالك لا تسمح باختلاق نص Gate A أو Gate B.
يجب استخراج النص الأصلي من ADR-023 ومراجعة سياقه.
إذا لم تجد النص الأصلي:
- ابحث في Git History.
- افحص الوثائق المرتبطة.
- افحص القرارات السابقة.
- افحص التقارير والأرشيف المتاحين.
- حدد موضع النقص.
- لا تنشئ تعريفًا مزيفًا للبوابة.
## 2.5 مسار التعامل مع النص الأصلي المفقود لـ Gate A/B
إذا لم يوجد النص الأصلي بعد البحث الموثق في:
1. ADR-023.
2. Git History.
3. الوثائق المرتبطة.
4. القرارات المعمارية السابقة.
5. التقارير والأرشيف المتاحين.
سجّل إحدى الحالتين:
`GATE_A_TEXT_NOT_FOUND`
أو:
`GATE_B_TEXT_NOT_FOUND`
ويجب أن يتضمن سجل البحث:
- الأماكن التي تم البحث فيها.
- نطاق البحث وتاريخه.
- المراجع والملفات التي تم فحصها.
- ما تم العثور عليه.
- ما تم استبعاده وأسباب استبعاده.
- هل البحث شامل أم محدود بسبب عدم توفر مصدر.
بعد ذلك:
1. لا تخترع النص الأصلي.
2. لا تتوقف عن بقية الأعمال.
3. حدد المشكلة الهندسية الفعلية التي يمكن إثباتها.
4. استخرج المتطلبات المنطقية من القرارات المعتمدة الأخرى.
5. صمم قرارًا هندسيًا جديدًا عند الحاجة.
6. صنف القرار صراحةً:
   `NEW_ENGINEERING_DECISION`
7. وثق مصادر المتطلبات والافتراضات وحدود المعرفة.
8. نفذ القرار واختبره إذا كان قابلًا للتنفيذ.
9. اربط القرار بالمعايير التي يعالجها.
**قاعدة إلزامية:**
القرار الهندسي الجديد ليس نصًا أصليًا مسترجعًا، ولا يُعتبر بديلًا تاريخيًا عنه.
ولا يمنح القرار الجديد حالة PASS تلقائيًا.
يجوز إعلان PASS لمعيار Gate المرتبط فقط إذا أمكن إثبات استيفاء معيار الخروج من:
- تعريف أصلي تم العثور عليه؛ أو
- مصدر معماري معتمد آخر يثبت متطلباته؛ أو
- تعريف بديل اعتمده المالك صراحةً.
إذا تعذر إثبات التكافؤ أو شروط القبول، تبقى الحالة PARTIAL أو BLOCKED وفق طبيعة النقص.
يُرفع للمالك أي تغيير مطلوب في معيار القبول نفسه، مع الاستمرار في تنفيذ الأعمال المستقلة.

## 7.1 معيار القبول لـ Gate A — Acceptance Contract
قبل إعلان PASS، أنشئ Acceptance Contract يتضمن:
- النص الأصلي أو حالة `GATE_A_TEXT_NOT_FOUND`.
- المصدر المرجعي لكل متطلب.
- المشكلة المعمارية.

- تصنيف القرار: أصلي أو جديد.

- الأدلة المطلوبة.
- الاختبارات المطلوبة.

- Blockers المتبقية.
- أثر القرار على P1-EXIT-02 والمعايير التابعة.
الحالات التشغيلية للقرار:
- `DECISION_PENDING`
- `DECISION_DOCUMENTED`
- `DECISION_IMPLEMENTED`
- `DECISION_VERIFIED`

**BLOCKED** إذا لم يوجد قرار صالح أو بقي مانع إلزامي يمنع الاستيفاء.
لا تفترض أن كل Gate يحتاج الاختبارات نفسها؛ استخرج متطلب الاختبار من تعريف القبول المعتمد.

# القسم 25 — التفويض الكامل لعمليات Git Commit وPush
يمنح مالك المشروع Cursor تفويضًا صريحًا ومسبقًا لتنفيذ عمليات Git Commit وGit Push تلقائيًا دون طلب إذن إضافي، متى استوفت التغييرات شروط الجودة والسلامة المحددة في هذا القسم.
هذا التفويض جزء من صلاحيات التنفيذ الهندسي الكاملة لإغلاق Phase 1.
## 25.1 Commit Authorization
يحق لك تنفيذ Commit دون الرجوع إلى المالك إذا تحققت جميع الشروط التالية:
1. التغييرات مرتبطة بنطاق Phase 1.
2. التنفيذ متوافق مع ADR-023 وقرارات المالك المعتمدة.
3. الاختبارات المطلوبة للتغييرات ناجحة.
4. اختبارات Regression ذات الصلة ناجحة.
5. تمت مراجعة الكود وGit Diff.
6. لا توجد أخطاء معروفة غير معالجة ناتجة عن التغييرات.
7. لا توجد Secrets أو Credentials أو ملفات .env.
8. لا توجد قواعد بيانات تشغيلية محمية ضمن الملفات المراد الالتزام بها.
9. لا توجد ملفات WIP غير مراجعة أو غير مفهومة ضمن Staging.
10. الوثائق متوافقة مع التنفيذ الفعلي.
11. تم التحقق من سلامة الملفات المعدلة.
12. تم تحديد الملفات المراد الالتزام بها باستخدام Scoped Staging.
إذا استوفت التغييرات هذه الشروط، نفذ Commit مباشرة دون انتظار موافقة إضافية.
## 25.2 Push Authorization
يحق لك تنفيذ Push تلقائيًا بعد نجاح Commit والتحقق من الشروط التالية:
1. الفرع المستهدف هو فرع المشروع الصحيح.
2. Remote Repository صحيح.
3. لا توجد تغييرات غير ملتزمة يجب الحفاظ عليها ضمن عملية الدمج.
4. لا يوجد تعارض غير معالج مع Remote.
5. الاختبارات المطلوبة ناجحة.
6. Commit تمت مراجعته.
7. لا يتضمن Commit بيانات محمية أو أسرارًا أو WIP غير معتمد.
بعد استيفاء هذه الشروط، نفذ Push مباشرة دون طلب إذن إضافي.
## 25.3 قواعد Staging
ممنوع استخدام:
```bash
git add .
git add -A
```
استخدم Scoped Staging فقط.
قبل Commit افحص:
```bash
git status --short
git diff --cached --stat
git diff --cached --name-status
git diff --cached
```
راجع كل ملف موجود في Staging.
لا تلتزم بملفات غير مرتبطة بالمهمة.
لا تلتزم بقواعد البيانات المحمية أو ملفات البيئة أو الأسرار.
## 25.4 قواعد Commit
استخدم رسائل Commit واضحة تصف التغيير.
يفضل تقسيم العمل إلى Commits منطقية مستقلة عندما تكون التغييرات متعددة المسؤوليات.
لا تجمع تغييرات غير مترابطة في Commit واحد لمجرد تسريع العمل.
لا تعدل تاريخ Git السابق.
ممنوع:
- `git reset --hard`
- `git clean -fd`
- `git clean -fdx`
- `git push --force`
- `git push --force-with-lease`
## 25.5 معالجة Push Conflicts
إذا ظهر اختلاف مع Remote:
1. افحص سبب الاختلاف.
2. حدد الالتزامات والملفات المتعارضة.
3. حافظ على جميع الأعمال المحلية والبعيدة.
4. نفذ الدمج الآمن وفق استراتيجية Git المناسبة.
5. لا تستخدم Force Push.
6. أعد الاختبارات المتأثرة.
7. نفذ Push بعد التأكد من سلامة النتيجة.
إذا تعذر حل التعارض بأمان، لا تخاطر بالتاريخ أو WIP.
وثق المانع وأكمل الأعمال المستقلة.
## 25.6 التوثيق بعد Commit وPush
بعد كل عملية ناجحة، سجل:
- Commit Hash.
- Commit Subject.
- Branch.
- الملفات التي دخلت Commit.
- نتائج الاختبارات.
- Push Result.
- Remote Branch.
- Sync Status.
- تاريخ ووقت التنفيذ.
حدث:
`docs/phase-1-progress.json`
وحدث Blocker Register أو Gap Closure Matrix عند الحاجة.
احفظ تقرير Commit/Push داخل FilesystemMissionArtifactArchive وتحقق من سلامة الأرشفة.
## 25.7 التفويض لا يلغي الحماية
التفويض بتنفيذ Commit وPush لا يسمح بـ:
- Force Push.
- حذف WIP.
- حذف قواعد البيانات.
- الالتزام بالأسرار.
- الالتزام بملفات غير مراجعة.
- تجاوز الاختبارات.
- إخفاء الاختبارات الفاشلة.
- الالتزام بتغييرات خارج نطاق Phase 1 دون مبرر.
عند استيفاء شروط النجاح، نفذ Commit وPush مباشرة دون انتظار المالك.
## 25.8 تقسيم الالتزامات
إذا كان العمل كبيرًا:
- أنشئ Commits صغيرة ومنطقية.
- اختبر كل مجموعة.
- لا تلتزم بتغييرات غير مكتملة.
- حافظ على تاريخ مفهوم.
- اربط كل Commit بالمعيار الذي يخدمه.
إذا كانت هناك تغييرات مكتملة مستقلة عن معايير ما زالت BLOCKED، يجوز الالتزام بالتغييرات المكتملة بعد اجتياز شروطها.
لا تجعل Blocker مستقلًا يمنع Commit لتغيير صحيح ومكتمل، ما لم يكن هناك اعتماد تقني أو تعارض مثبت.
## 25.9 الفصل بين جاهزية التسليم وإغلاق المعيار
استخدم الوصف التشغيلي:
`DELIVERABLE_READY`
للدلالة على أن مجموعة تغييرات مكتملة وجاهزة للالتزام Git.
هذا الوصف:
- ليس حالة PASS جديدة.
- لا يثبت إغلاق P1-EXIT.
- لا يلغي Blocker.
- لا يعني اكتمال Phase 1.
يمكن أن تكون بعض التغييرات `DELIVERABLE_READY` بينما يبقى معيار مستقل `BLOCKED`.
لا تمنع Blockers غير المرتبطة الالتزام بالتغييرات المكتملة والمؤهلة.
