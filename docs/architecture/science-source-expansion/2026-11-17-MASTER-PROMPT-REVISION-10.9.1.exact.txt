## 14.4 SQLite Lock, Hung Diagnostic Processes & Ingestion Continuity Protection
The project contains critical SQLite persistence and archival data. SQLite locks and diagnostic processes must be handled without interrupting active ingestion or damaging persistence state.
### A. Process Identity Verification
Before terminating any process inside Docker:
1. Identify the exact container.
2. Verify that the PID exists.
3. Read its complete command line and process identity.
4. Determine whether it is:
   - A diagnostic PRAGMA probe.
   - A read-only WAL inspection.
   - A Laravel Artisan process.
   - An active Ingest Writer.
   - A persistence or archival process.
5. Never infer process identity from PID alone.
6. Never terminate a process whose identity is unknown or ambiguous.
### B. Safe Process Termination
For a positively identified hung diagnostic process:
1. Attempt SIGTERM first.
2. Wait and recheck the same process.
3. Use SIGKILL only if that exact diagnostic process remains unresponsive and its identity is reconfirmed.
Never terminate an active Ingest Writer, Laravel ingestion process, persistence worker, or archival writer merely because it holds a SQLite lock.
If process identity cannot be established, do not terminate it. Continue with safe diagnostics.
### C. SQLite and WAL Protection
1. Preserve the SQLite database.
2. Preserve associated WAL and SHM files.
3. Never delete, replace, truncate, or manually modify these files.
4. Do not run destructive SQLite repair or checkpoint operations.
5. Perform WAL inspection in read-only mode only after confirming that no active writer is operating on the same database.
6. Do not repeatedly launch PRAGMA probes that remain hung or compete for database locks.
7. Record the exact database path and process ownership.
8. Verify database accessibility without interrupting active ingestion.
### D. Ingestion Continuity
Before launching any new Persist or Ingest window:
1. Read the existing manifest and checkpoints.
2. Verify the last completed window.
3. Determine the exact completed package range.
4. Determine the next unprocessed package range.
5. Verify that no previous writer remains active.
6. Verify checkpoint consistency.
7. Confirm that the next operation will not duplicate completed packages.
8. Launch the next bounded operation exactly once.
9. Verify actual checkpoint advancement and log output.
Never restart a completed window or repeat completed packages unless a concrete integrity failure proves that recovery is necessary.
### E. Evidence and Recovery
Record:
- Database identity and path.
- Container identity.
- Process PID and full command line.
- Process classification.
- Writer status.
- Lock observations.
- WAL inspection results.
- Checkpoint values before and after ingestion.
- Completed and newly processed package ranges.
- Actual command and exit status.
- Recovery actions and evidence.
Never claim that SQLite is unlocked or healthy without actual verification.
Preserve all original evidence and ingestion logs.
